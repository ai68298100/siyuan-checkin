日期：2026-10-12。本文只列小驴打卡提供端需要修复、说明和验证的内容，可直接转发给小驴作者。

**2. 日历：补齐远端合并后的刷新通知**

当前 `reconcileStore()` 通过 `enqueueMutation()` 读取并合并远端存储。已有流程会使本地 store 更新，并刷新小驴自己的页面，但没有向集成消费者广播变化。

复现结果：远端把项目名从 `before` 改为 `after-remote-edit`，执行实际 `reconcileStore()` 后，`getItems()` 已返回新名称，而订阅者收到的事件数组仍为空。

修复建议：

- 在已有合并流程的“远端数据导致本地 store 变化”分支中，完成合并和必要的摘要失效处理后，广播一次现有 `analytics-updated` 数据事件。
- 同一逻辑也应覆盖后续写入前的远端合并，不能只修窗口 focus 入口。
- 无数据变化时不广播。通知允许粗粒度，不必为判断是否通知而重新计算全日历。
- 有远端变化时，即使后续业务操作失败，也应通知消费者当前可读数据已经变化；卸载后停止广播。
- 继续保持 `api.subscribe()` 的 `event.type` 不带 `checkin:`，window CustomEvent 名带 `checkin:`。

建议沿用现有数据事件，不增加一套远端同步事件体系。七类数据事件白名单保持兼容。

验收：名称、可见性、归档、恢复、记录新增和删除通过远端合并进入本窗口后，消费者能重新读取最新投影；无变化的合并不会触发刷新循环。

**3. 生命周期：增加一个明确的状态通知**

建议新增一个 window 生命周期事件，名称固定为 `checkin:api-state-changed`。这是拟新增契约，v18.17.3 尚未提供。

```ts
type CheckinApiStateChange = {
  state: "loading" | "ready" | "failed" | "unavailable";
  version: number; // API 协议版本，例如 5
};
```

触发时机：

- 发布 `window.siyuanCheckin` 并开始初始化后：`loading`。
- 存储初始化完成、`isReady()` 已为 true 后：`ready`。
- 初始化或重新初始化失败、`whenReady()` 的失败结果已确定后：`failed`。
- 卸载时，停止接收操作并移除自身持有的全局 API 后：`unavailable`。

该通知作为 window 层的生命周期信号，保留 `api.subscribe()` 现有的数据事件语义。可在 `describe()` 中增加可选的 `lifecycleEvents` 字段说明它，不向既有数据事件联合类型塞入未经处理的新类型。

注意实现细节：

- 卸载通知应能在 `disposing` 状态下发送，不能被现有 `broadcast()` 的退出判断吞掉。
- 仅移除本实例持有的全局 API，避免旧实例卸载时删除新实例的 API。
- 旧实例已经被新实例替换时，只清理自身资源，不广播代表当前全局会话的 `unavailable`。
- 生命周期事件只表示“需要重新探测”。消费者以当前全局 API、`isReady()` 和 `whenReady()` 的布尔结果判断是否可用。
- `whenReady()` 返回 false 必须视为未就绪；初始化失败后的重试需要更新就绪 Promise 并再次发送状态通知。

为保持 v5 兼容，本轮不强制改变所有既有读取 API 的返回类型。文档应明确：旧引用还能返回数据，不代表它仍是有效会话；有效会话必须是当前 `window.siyuanCheckin` 且 `isReady()` 为 true。

验收：两种插件加载顺序、初始化失败后重试、卸载、热重载、旧实例迟到卸载均能正确通知，事件不泄露 store 或私人数据。

**4. 投影：保留兼容输出，补齐准确的状态说明**

目前配额分支的 `complete` 表示该日有正值记录，不代表周/月配额已达成；`quotaRate` 保存周期累计进度值，不是 0～1 的比例。

建议本轮采用兼容修订：

- 保留既有六种状态以及 `quotaRate` 字段的数值含义，不在同一 API 版本中悄悄改成百分比。
- 在 v5 文档明确：普通排期项目的 `complete` 表示达标；配额项目的该日 `complete` 表示有记录，应展示“已记录”。
- 为每个 point 增加 `scheduleType`，取该日期有效修订的排期类型。项目顶层 `scheduleType` 取范围末日，不能用于解释整个历史范围内的所有 point。
- 在投影顶层增加 `asOfDate`，取本次读取时的宿主本地日。未来日期应展示为计划/未来状态，不能把无记录的 `at-most-safe` 宣传为已经达成。
- 所有新字段从现有规则函数派生，不维护第二套排期或完成计算。
- `quotaRate` 的兼容说明要注明它对应范围末日所在的周期；本轮不要求消费端绘制配额百分比。

拟新增字段示意：

```ts
{
  asOfDate: "2026-10-12",
  // 既有范围、项目和截断字段保持兼容
  items: [{
    points: [{
      date: "2026-10-11",
      scheduleType: "quota", // 从该日有效修订取得
      status: "complete",
      value: 1,
      target: 10,
      unit: "个"
    }]
  }]
}
```

验收：周配额 1/10 显示为该日已记录；跨越 quota→daily 修订的历史范围能逐日解释；未来戒除日期不显示为已完成。继续验证隐藏、归档过滤以及返回值的防御性副本。

如果之后希望把配额日状态统一改为 `logged`，或把 `quotaRate` 改为比例，应另做版本化语义迁移。本轮优先采用上述增量修订。

**5. 批量写入：统一身份解析和日期有效规则**

已复现的差异：

- `taskhorizon:bad:block:2026-02-30`：单条接口拒绝，批量接口产生新记录。
- 项目现在是 `atLeast`、历史修订是 `atMost`：历史批量记录被接受。
- 项目现在是 `atMost`、历史修订是 `atLeast`：历史批量记录被阻止。
- 项目只在周一排期：周日批量记录被接受，随后投影显示 `logged`。

建议抽取或复用内部纯校验函数，供批量规划与参考 bridge 使用；本轮无需新增目标列表 API，也不要求消费端复制修订解析算法。

基础修复：

- 对 `taskhorizon:` 前缀，复用单条接口的严格解析函数，验证块身份、有效日历日期、长度和字符限制。
- API 仍以显式 `occurredAt` 推导实际落账日；externalRef 的日期不是落账参数。
- 批量方向检查改用写入日期的有效修订，单位也从同一修订取得。
- 不把“该日项目存在且未处于归档区间”误写成“该日符合星期/间隔排期”。两种检查的含义和失败原因需要区分。

普通任务完成合作的首次范围固定为：`count + daily + atLeast`。小驴已有“任务打卡”模板就是每日次数项目，可继续使用并调整目标 N。

对新的 Task Horizon 完成事实，提供端应明确校验：

- 输入提供有效、带时区的 `occurredAt`，合作写入不使用调用时刻兜底。
- 普通任务完成的 `value` 固定为 1，`unit` 显式提供；按通用格式校验后，再用该日有效单位校验，避免配置变化后静默换算。
- 目标存在且当前未归档；记录日期不早于创建日，也不位于归档区间。
- 该日有效修订是每日次数、正向累计项目，且输入单位与有效单位一致。
- 该日已 SKIP 时返回可处理的阻塞原因，不自动撤销 SKIP。
- 输入日期不是未来日；externalRef 的日期与按宿主时区推导的落账日一致。时区变化造成不一致时，应明确阻塞，不能静默改日或改身份。

新增合作限制仅针对 `taskhorizon:` 来源。其它来源仍可按原通用 API 规则记录非排期事实；不要为了本合作破坏 `logged` 的通用用途。

Task Horizon 同一身份的既有事实应先得到回执，再判断“是否允许创建新事实”。建议对本合作固定判定顺序：输入格式校验 → 同身份墓碑 → 已存事实/批内重复 → 新事实业务校验 → 规划写入。正常化存储应消除墓碑与存活事件并存的矛盾；命中墓碑时不得重放。

项目后来归档、单位后来变化，不能导致已经存在的事实无法返回 `duplicate`。日期与身份一致性等新事实检查也不能覆盖已有事实回执。

失败原因应复用现有 reason 风格，补齐必要的身份、日期、项目类型、SKIP 等原因，并在 fixture 中冻结字符串。建议保持逐条 `blocked/rejected` 与主机级 Promise 拒绝的区别。

**6. 批量回执：修复成功 resolve 为 undefined 的路径**

本次进一步复现：`recordEventsBatch()` 起始状态为 ready，但 `enqueueMutation()` 的存储刷新阶段失败。底层队列吞掉刷新异常并返回 undefined，公共批量方法也成功 resolve 为 undefined。

这与“批量逐条结果严格一一对应，主机失败 reject”的合作约定不一致。

建议在批量公共边界检查结果，不必把所有内部 mutation 的兼容行为一起改掉：

```ts
const results = await enqueueMutation(() => executeBatch(snapshot));
if (!Array.isArray(results) || results.length !== snapshot.length) {
  throw new Error("checkin: batch was not executed");
}
return results;
```

以上是结构示意，实际使用现有批量实现和错误体系。

- 顶层非数组或超过批次上限：Promise reject。
- 单条输入格式或业务条件失败：返回该条 `rejected/blocked`。
- 未就绪、卸载、刷新失败、持久化失败、队列未执行：Promise reject。
- 正常返回时，数组长度与捕获的输入长度相同，`recorded/duplicate` 必须带有效 `eventId`。
- 批内重复身份也必须回填同一事件身份。
- Promise 拒绝只说明没有获得成功回执，不能保证远端一定没有发生写入；重试必须保留原身份。

验收：覆盖刷新失败、排队期间卸载、持久化确认失败以及业务提交成功后反馈阶段失败，不能出现 undefined 被当作正常批量结果。

**7. 批量输入：调用时捕获快照**

已复现：调用 `recordEventsBatch(inputs)` 后、队列实际执行前，将 `inputs[0].value` 从 1 改为 7，最终事件值为 7。输入数组长度也可能在顶层上限检查后变化。

修复建议：

- 在首次异步排队前复制输入数组和各条输入对象。
- 允许的输入字段均为标量，浅复制即可，不需要引入通用深克隆库。
- 批次上限检查、逐条规划、结果顺序和结果长度都以该快照为准。
- 数组中的非法元素仍交由逐条校验，保留一一对应回执。

示意：

```ts
const snapshot = Array.from(inputs, input =>
  input && typeof input === "object" && !Array.isArray(input)
    ? { ...input }
    : input
);
// 后续仅使用 snapshot，包含上限检查和 enqueueMutation 回调。
```

验收：调用后修改 value、unit、occurredAt、externalRef 或增删输入元素，均不能改变已经提交的批次含义和长度。

**8. 重试归属：保留旧兼容行为，普通任务合作采用批量接口**

已确认单条 `recordEvent()` 持久化失败后会进入小驴的 external pending box；初始化时的 `recoverExternalPendingBox()` 会自动恢复。模拟首次失败、随后恢复后，原记录被实际补写。

因此，消费端单方面“丢弃待处理项”无法撤销小驴单条接口内部已经保存的副本。

本轮建议：

- 普通任务完成合作只使用 v5 `recordEventsBatch()`，包括只有一条记录的情况。
- 确认并用测试锁定：批量失败不会进入小驴内部的单条 external pending box，也不会在小驴启动时偷偷自动恢复该批。
- 普通任务的待处理和手动重试由消费端负责；小驴继续负责最终身份去重、墓碑和逐条回执。
- 保持其它来源和旧单条接口的恢复机制兼容，不全局关闭待处理箱。
- 把单条 `undefined` 的说明改为“本次未取得成功回执”；项目归档后重复调用单条接口就可能出现该情况，而原事实仍存在。

本轮不需要新增公开的“丢弃批量队列”或撤销 API。解除绑定、关闭联动和消费端丢弃队列都不是撤回已经写入的小驴事实。

**9. 发布识别与文档修订**

现有 v18.17.3 已经声明 API v5 和相关基础能力，消费端仅检查 `version >= 5` 无法识别上述修复是否已经完成。

建议在 `describe()` 中添加一个可选、很小的合作契约标记：

```ts
integrationContracts: {
  taskHorizonCalendar: 1,
  taskHorizonCompletion: 1
}
```

这是拟新增字段，不是目前已有能力。日历修复和对应 fixture 通过后先发布 `taskHorizonCalendar: 1`；回写修复通过后再发布 `taskHorizonCompletion: 1`。尚未完成的标记省略。该字段和契约 fixture 使用同一组常量，避免额外维护版本分支。

这一增量标记不替代 `protocol/version/capabilities`，也不改变旧消费者使用基础 v5 的方式。新增生命周期和投影字段保持兼容；若另行改变已发布字段的含义，需要按已有版本政策做迁移。

两份文档同时修正：

- 普通“每天完成 N 个任务”使用每日次数项目，不描述为周/月配额项目。
- 非法日期、空区间和反向区间拒绝；超过 366 天返回截断结果。最多 200 个可见项目，超出同样明确 `truncated`。
- 解释 `quotaRate` 是累计量，解释配额日的 `complete`。
- 读日历和回写两个授权开关独立；项目级日历隐藏不控制回写。
- 说明生命周期通知、跨窗口合并刷新和失败回执。
- “数据不经内核”改为“使用思源插件独立数据存储，不依赖笔记块”；实际持久化使用思源 `saveData`。
- 删除“项目级可见性还待设计”等过时段落。
- 保持旧 v4 manifest 的兼容定义；v5 合作扩展与修复 fixture 单独说明。
- 示例、fixture 和源码链接固定到修复发布 tag/commit；区分提供端验证与双方现场联调。

**10. 验收清单与交付顺序**

| 类别 | 必须覆盖的场景 | 期望结果 |

| 日历同步 | 远端修改名称/可见性、归档/恢复、增删记录 | 本窗口得到刷新信号并读到新投影 |

| 身份 | 非法块身份、非法日历日期、过长身份、批内重复 | 拒绝非法身份；重复不增账 |
| 修订 | 历史 atMost→当前 atLeast 及反向情况 | 按历史有效修订判断新事实 |
| 合作目标 | 非每日次数、归档、删除、单位变化、创建日前、SKIP | 返回明确阻塞；不自动改变项目状态 |
| 日期 | 显式历史时间、跨午夜、无时区时间、未来日、时区改变 | 原时间身份稳定；无效或不一致输入明确失败 |
| 幂等回执 | 记录后归档、单位变更、删除墓碑后重放 | 已存事实返回 duplicate；墓碑阻止重放 |
| 主机失败 | 存储刷新失败、排队期间卸载、落盘确认失败 | 批量 reject，不 resolve undefined |
| 输入快照 | 调用后修改字段/增删元素 | 已提交含义和结果长度不变 |
| 重试归属 | 批量失败后重载小驴 | 小驴没有独立自动补写副本 |
| 兼容性 | 旧单条接口、其它来源、通用非排期 logged | 合作修复不破坏既有来源行为 |

建议分两批提交，便于独立验收：

1. 日历提供端：完成 C-01～C-04、生命周期通知、增量投影字段、日历契约标记及 fixture，然后发布可识别的修复版本。
2. 普通任务回写提供端：完成 W-01～W-06、调用时输入快照、明确逐条回执和主机失败行为，然后发布回写契约标记及 fixture。

每批附上源码 commit、发布 tag、fixture、测试命令和结果。真实思源宿主至少覆盖桌面、独立窗口和移动端；把当前数据窗口的广播测试与真实跨窗口数据合并测试分开报告。

内部打卡循环的撤回、恢复、双向同步和历史全量对账留到后续独立契约，不作为这两批提供端修复的前置条件。

# 同步设计评审稿（T-1370，2026-09-21）

> 状态：**评审稿，结论已按既定决策门出具**。本文回答 v22 决策门的两个问题——「要不要做同步」「如果做，边界是什么」。结论：**不立项自建同步**；跨设备场景由思源同步承载，插件侧以可解释性与恢复能力配合。
> 决策记录：D-243。若未来推翻本结论（例如用户明确要求独立同步），须以新决策记录重启设计，本文降级为历史输入。

## 一、现状盘点（设计前的事实）

1. **数据已在宿主同步范围内**：插件全部数据（主存储、恢复点、事项、偏好、审计）经 `saveData/loadData` 写入思源工作区 `data/plugins/` 目录——用户开启思源同步（官方/WebDAV/S3）时，这些文件**天然随工作区跨设备**。这是现状，不是假设。
2. **单设备多窗口已有一致性机制**：Web Locks 存储锁 + 写前重读合并（`enqueueMutation`）+ 冲突审计（`version-conflict` 诊断与 `type: "conflict"` 审计）。
3. **跨设备冲突的既有语义**：思源同步在两端都改了同一文件时做合并/留副本；插件在 `onDataChanged` 收到变更后走 `reconcileNormalizedStoreSnapshots` 重读合并，保证最终一致（已有多窗口等价路径与测试）。
4. **恢复点为本地文件**（`checkin-store-backup`），随工作区同步；导出的 JSON 备份是用户自管的迁移通道。
5. **本会话新增**：诊断原因码（`getDiagnostics`）、审计导出、数据恢复指南——跨设备故障的可解释性基础已在。

## 二、方案选项与五维评估

评估维度：隐私边界 / 冲突语义 / 撤销能力 / 数据所有权 / 密钥与运维成本。

| 维度 | A. 现状+改进（思源同步承载） | B. WebDAV 快照通道 | C. 端到端加密自建同步 |
| --- | --- | --- | --- |
| 隐私 | 数据不出用户配置的同步范围；无新增出站通道 | 数据出站到用户配置的第三方盘；明文快照 | 出站到自建服务端；密钥在客户端 |
| 冲突 | 宿主合并 + 插件重读合并 + 诊断/审计（已有） | 自建：需要时间戳/向量时钟策略与"副本文件" UX | 同 B 且更复杂 |
| 撤销 | 恢复点 + 导出备份（已有） | 需要服务端版本历史，插件不可控 | 需要服务端 |
| 数据所有权 | 用户工作区，完全自持 | 第三方盘 | 自建服务端 |
| 成本/运维 | 零新增 | 中（协议适配+定时器+错误处理） | 高（账号≠账号体系红线冲突风险、密钥托管、服务器） |

## 三、结论（按 D-243 记录）

1. **不立项自建同步服务**（含 C 类端到端加密自建通道）——与「不自建同步服务、无账号体系」的全版本边界一致；跨设备场景由 **思源同步承载**：插件数据天然位于工作区，用户开启宿主同步即获得跨设备。
2. **立三个配套改进项**（小步，随 18.x/19.x 常规迭代，不单开版本）：
   - 跨设备冲突可解释性：`version-conflict` 诊断与冲突审计已落地，补充冲突发生时的用户文案（说明"另一设备/窗口的修改已合并，可在审计中查看"）；
   - 恢复点跨设备语义声明：在《数据诊断与恢复指南》中说明恢复点文件随思源同步走、恢复操作仅作用于本机；
   - 「导出即迁移」定位强化：JSON 备份已是跨设备/跨实例迁移的显式通道，保持单向快照语义，不做双向同步。
3. **智能体与同步的关系**：智能体诊断（T-1361）只解释冲突原因码与建议顺序，不介入宿主同步行为（AI 规划 D 块边界延续）。

## 四、若未来重启同步立项的先决条件

- 用户明确的跨设备需求与可接受的冲突 UX；

- 宿主同步被证实不足（例如需要只同步本插件数据的场景）；

- 新决策记录包含：密钥/加密方案、服务端形态、账号边界豁免论证、迁移与退路。

## T-1463 合并语义参考（PixelHabits 三段式，2026-09-26）

> 设计参考记录，不实现同步（D-243 维持不立项）。来源：enjo2/PixelHabits README（2026-09-25 访问）——单 JSON 文件 + AES-256-GCM 导出包经任意共享文件夹同步，是本轮调研中唯一给出完整冲突解决规则的开源实现。

若未来多仓/多端合并成为需求（例如思源同步分叉后的工作区合并），参考其三段式语义映射到本插件事件模型：

1. **每日打卡取并集**（done anywhere = done）：同项目同 localDate 的完成事实在任一端存在即成立——与本插件「事件不可变、合并按身份去重」口径天然一致，且与 SKIP 容错（maxGap）不冲突（SKIP 是显式事件，两侧都有时按修订时间取新）。
2. **元数据按 `updated_at` 后写胜出（LWW）**：项目名称/图标/排期等修订元数据以较新 `updatedAt` 为准——对应本插件 revisions 的 `effectiveDate` + `updatedAt` 双字段，LWW 需同时比较两者避免旧排期覆盖新排期。
3. **事件按 id 幂等去重**：事件以稳定 id 为唯一身份，重放/重导入不产生第二条——本插件已有 `source + externalRef` 幂等与墓碑机制，是同语义的更强形态。

配套护栏（与本插件既有纪律对齐）：合并前自动快照（既有恢复点）、合并报告可见（冲突不静默）、墓碑优先于并集（已删除事件不复活）。

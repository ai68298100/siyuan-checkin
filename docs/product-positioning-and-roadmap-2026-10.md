# 小驴打卡：产品定位、能力边界与下一阶段路线

> 版本：v3 设计决策稿 · 2026-10-07
>
> 本文把仓库现有能力、已完成的内部研究和 GitHub 一手资料合并为一个产品判断。它服务于产品、交互和工程决策；示例数据只用于说明界面，不代表真实用户数据。

## 1. 先给结论

**小驴打卡是思源里的低压力个人行动台：把今天要做的事变成可追溯事实，再用笔记、外部来源和复盘把事实转成下一步。**

它的核心价值不是比普通习惯应用多一张热力图，而是把「行动、证据、上下文、调整」连成一条可回到原文的闭环：

```text
定义一个想持续做的项目
  → 今天只呈现可执行的一小步
  → 低摩擦记录事实（手动、专注、文档块或外部来源）
  → 事实带来源、日期、单位和撤销路径
  → 回顾区分事实 / 推断 / 建议
  → 用户决定是否调整未来规则
```

对外可用的短句是：**在思源里，轻松记录今天，找回事实，再决定下一步。**

## 2. 为什么要改定位

当前实现已经覆盖二值、次数、数量、时长、自定义记录，六类排期、跳过、戒除/上限、提醒、专注、回顾、洞察、事项、归档、模板、导入导出、笔记锚点、渲染块、API v5 和多个来源适配器。继续把它包装成“习惯打卡工具”，会让用户拿它和 Loop、Streaks、Habitify 比连续天数、徽章和同步数量，反而掩盖了真正的优势。

仓库源码和任务台账显示，事件模型是私有事实源，记录带 `localDate`、`source`、`externalRef`、备注和撤销/审计路径；笔记锚点、报告、渲染块和公开 API 负责把事实带回思源生态。这个组合更接近“行为证据层”或“个人行动台”，而不是一个孤立的清单。

## 3. 调研方法与证据口径

本次增量调研只把公开 README、源码/文档和公开 issue 作为能力证据，不把星数、营销语句或未实测的宿主表现当作稳定契约。商业竞品和既有本地研究作为交互线索，最终判断以本仓库的数据模型、现有功能和低压力基线为准。

| 资料 | 已确认的可借鉴模式 | 对小驴打卡的限制 |
| --- | --- | --- |
| [Loop Habit Tracker](https://github.com/iSoron/uhabits) | 离线、无账号、灵活频率、提醒、统计、CSV/SQLite 导出；完成、跳过和无数据有区别 | 复杂周期、提醒和组件边界容易产生错误，必须在 UI 中展示规则与来源 |
| [InlitX/Streak](https://github.com/InlitX/streak) | 一键记录、普通/避免/数值三类项目、备份、专注计时、年度热力图 | 离线能力和快速入口值得吸收，计时、通知和状态长按需要明确失败语义 |
| [Habitica](https://github.com/HabitRPG/habitica) | Habits、Dailies、To-Dos、Rewards 的分层和正向反馈 | RPG 惩罚、连带压力和复杂奖励不符合本产品的低压力边界 |
| [Siyuan Task Assistant](https://github.com/MoonBottle/siyuan-plugin-bullet-journal) | 原生块标记、多视图、任务/日历/专注/习惯聚合 | 功能面很宽；小驴只接入公开契约，不复制对方私有存储或内部 DOM |
| [Siyuan Task List](https://github.com/syh19/siyuan-plugin-task-list) | 按文档/笔记本/工作空间聚合，点击任务回到源文档并定位 | 回源跳转、手机端和同步失败必须有可见的降级路径 |
| [Obsidian Tracker](https://github.com/pyrochlore/obsidian-tracker) | 声明式数据源、趋势/月视图、按字段聚合 | 统计必须带数据集、分母和更新时间；不能把无数据误画成未完成 |
| [Heatmap Calendar](https://github.com/Richardsl/heatmap-calendar-obsidian) | 热力图适合发现长期节奏 | 热力格必须可钻取到日期和原始事件，不能停留在装饰图 |

既有仓库研究还验证了三个方向：Loop 的宽容状态、笔记插件的回源定位，以及本地优先的导入/导出所有权。对应的反面经验是：复杂周期、自动来源、跨窗口和移动跳转最容易把“看起来聪明”变成不可解释的错误。

## 3.1 旧原型具体掉分项

这不是“风格不够高级”的笼统判断，而是从 v2 页面结构、当前功能清单和竞品交互逐项得到的差距：

| 旧原型问题 | 用户实际负担 | v3 调整 |
| --- | --- | --- |
| 六个页面并列导航，Editor/Focus/AI 又藏在按钮里 | 用户需要先理解页面枚举，才能猜入口 | 一级只保留今天/回顾/事项/设置；上下文页带返回栈进入 |
| Today 摘要、提醒、同日历史、未来负荷和清单都争夺首屏 | 看到很多数据，却不确定下一步该点哪里 | 顶部只有一个下一步卡；证据轨默认收起 |
| Review 图表和项目卡先出现，事实来源在后面 | 派生数字像结论，难以判断分母和能否回源 | 概览先列事实/范围/更新时间，分析后置并带依据 |
| 设置按内部模块列长表单 | 新用户要在 appearance、host、external 等实现词之间猜 | 健康总览 → 目标分组 → 单来源详情抽屉 |
| Editor 一次暴露模板、类型、排期、来源、锚点和危险操作 | 首次创建决策过多，预览与保存边界不清 | 定义 → 安排 → 连接 → 确认，未来 7 天预览先于保存 |
| 事项双栏在空态仍占据大块空间 | 空列表看起来像故障，移动端难以操作 | 列表优先；编辑抽屉可关闭；空态给模板/手动下一步 |
| 深色、跳过、部分完成、自动来源、失败等状态主要靠颜色 | 用户无法判断“没记录、跳过、失败、破戒”的区别 | 统一状态字典，文字 + 图形 + 位置三通道表达 |
| 高级能力没有独立的失败/恢复说明 | 自动来源和批量操作看起来像“已经成功” | 来源卡固定显示产生什么、写入哪里、最近结果和恢复动作 |

因此 v3 的“显贵”不是再加渐变和卡片，而是减少竞争、扩大信息层级差、让每个数字和动作都有来路和下一步。

## 4. 明确的产品定义

### 4.1 目标用户

1. 已经在思源记录工作、学习、阅读、运动或生活日志，希望知道“自己实际做了什么”的个人用户。
2. 不想被连续天数和红色逾期催促，但需要温和提醒、跳过、补记和可撤销修正的人。
3. 需要把自动来源、笔记块、专注时长和人工记录放在同一条可审计时间线上，又不愿把数据交给新的云端账号的人。

### 4.2 要解决的任务

| 用户时刻 | 用户问题 | 产品承诺 |
| --- | --- | --- |
| 打开插件 | 今天先做哪一件？ | Today 只突出一个下一步和一条主动作 |
| 刚做完 | 我记录成功了吗？来自哪里？能反悔吗？ | 写入状态、来源、影响和撤销都在结果附近 |
| 想复盘 | 这段时间到底发生了什么？ | Review 先给事实，再给口径，再给可选解释 |
| 想调整 | 我要改的是今天，还是未来规则？ | 编辑器先预览影响，历史事实不被静默改写 |
| 配置联动 | 自动记录是否真的在工作？ | 来源卡显示产生什么、写入哪里、最近结果和恢复动作 |

### 4.3 非目标

- 不做社交排名、排行榜、团队惩罚或 RPG 血量/金币系统。
- 不把任务管理、日历和笔记编辑器替代为第二套“全能工作台”。事项和外部工具作为辅助来源与入口。
- 不默认建立账号、自建云同步或上传完整备注；跨设备优先复用思源同步、用户选择的导出或公开契约。
- 不让 AI 静默改目标、排期、事件或文档。AI 只能生成带依据的草稿，用户确认后才写入。
- 不把没有记录、主动跳过、明确未达成和自动来源失败混成一个红色“失败”。

## 5. 三个产品支柱

### 5.1 今日行动：低压力地完成一小步

Today 的第一屏只服务当前行动：日期/时区、待处理数量、唯一主动作、项目队列和可撤销结果。提醒、事项、同日历史、未来负荷和建议都是证据层，默认折叠或放到次级轨道。

“记录”不是只有二值勾选，快速记录需要覆盖：完成一次、Add/Set 数值、时长、数量、自定义值、备注，以及专注结束后的确认。默认不要求填写理由，补记和跳过都必须是显式且低摩擦的动作。

### 5.2 证据回顾：事实 → 解释 → 下一步

Review 首屏先回答“发生了什么”：事实条数、项目数、来源数、日期范围和更新时间；第二层才展示完成率、趋势和热力图；分析卡必须显示数据范围、分母、来源、样本不足和回到事件的入口。

Insights 是单项目的长期解释页，属于 Review 的上下文页，不作为一级导航。任何建议都必须列出依据、影响范围、不确定性和用户动作；用户只看事实也能完成任务。

### 5.3 开放连接：私有事实源，公开可回源

事件事实由插件私有存储和审计路径负责；笔记锚点、渲染块、日记报告、Task Horizon、思阅、思播、健康、微信读书、叶归和 API v5 通过登记的来源/外部身份进入。外部来源必须可关闭、可诊断、可撤销、可去重，无法接入时手动记录仍可用。

## 6. 现有能力如何重新归类

| 产品层 | 当前能力 | 新 UI 归属 |
| --- | --- | --- |
| 核心行动 | Today、快速记录、补记、跳过、撤销、批量记录、拖拽排序、完成区 | Today + Quick record |
| 规则与计划 | 五类排期、配额、戒除/上限、优先级、提醒、模板、组合包 | Editor 的“定义 → 安排 → 连接 → 确认” |
| 证据与解释 | Review 概览/记录/分析、趋势、热力图、比较、成就、报告、助手 | Review；单项目进入 Insights |
| 日期上下文 | 生日、纪念日、还款、提醒事项、模板、完成/推迟 | Occasions，作为未来事项收件箱 |
| 笔记闭环 | noteAnchor、日记/摘要/问卷、渲染块、日期回源、API v5 | 来源卡、Evidence drawer、Block/Dock |
| 数据治理 | 归档/恢复、快照、导入导出、审计、诊断、删除影响 | Archive + Settings / Data center |
| 连接与专注 | Tomato、内置计时、思阅/思播/健康/微信读书/叶归、Agent | Focus、Integrations、Suggestion workspace |

## 7. 新信息架构

### 一级导航

1. **今天**：记录和处理当日机会。
2. **回顾**：选择范围，查看事实与证据。
3. **事项**：管理未来日期事项和提醒。
4. **设置**：体验、规则、连接、数据与诊断。

### 上下文入口

- `Insights` 从 Review 项目卡或 Today 证据卡进入。
- `Editor` 从 Today 的项目、模板或设置目标进入。
- `Archive` 从项目菜单或 Settings 数据中心进入。
- `Focus` 是项目行上的模式，不是一张需要独立维护的首页。
- `Suggestion workspace` 从 Review/Insights 的建议卡进入。
- `Quick record`、命令面板、Dock、嵌入块和移动底栏共享同一记录契约。

### 为什么不继续保留六个一级入口

当前原型把 Today、Review、Insights、事项、Archive、设置并列，又把 Editor、Focus、AI 隐藏在按钮里，用户需要理解内部页面枚举。新结构只把高频任务放在一级，其他页携带 `returnTo / itemId / localDate / range / source / scrollAnchor` 返回；这样减少认知入口，同时保留已有能力和深链。

## 8. 功能优先级与未来路线

路线按“要解决的用户风险”排，不把已经完成的能力重复包装成新增功能。

### P0：把核心闭环变得可理解

这是 v3 原型应先验证的范围，也是后续生产 UI 的第一批迁移候选：

- Today 的唯一下一步、快速记录和写入结果确认。
- 事实/规则/派生/建议的视觉和文案分层。
- Review 的“事实 → 依据 → 下一步”结构，所有指标可回源。
- Editor 渐进式向导和规则变更影响预览。
- 设置首页的健康状态摘要，外部来源进入详情而不是首屏堆满配置。
- 空库、筛选无结果、离线、失败、冲突、待同步和撤销状态。

验收重点：新用户能在一个模板或空白项目后完成第一次记录，并能从 Review 回到这条记录；失败重试不重复写入，关闭高级能力不影响手动记录。

### P1：让“调整”变成一个安全动作

这些是现有任务台账中仍有明确价值、但需要场景或真实体验验证的增强：

- **组合包部分应用与冲突预览**：先选择条目，再显示已有项目的规则差异；取消零写入，失败整批回滚。
- **导入错误行与截断预览**：把无法等价表达的字段、冲突和行号显示在确认前。
- **统一绑定抽屉与绑定体检**：从设置总览进入，显示目标、最近结果、失效原因和重新选择；不另造第二套绑定字段。
- **报告打印/PDF**：仅在用户需要纸面或共享复盘时立项，默认保留数据范围、生成时间、来源和回源链接。
- **“明确未达成及原因”研究**：先验证是否真的减少负担，再决定是否新增事件语义；不能把它自动当作 skip 或失败。

### P2：条件性生态能力

以下功能有价值，但依赖外部消费方、用户需求或真实宿主证据，当前写成候选而不是承诺：

- Task Horizon 实际消费端的日历图层、刷新和降级。
- 绑定同步后的自动体检和统一重试入口。
- 项目级 Pause、Exactly 精确达标、连击历史最小长度、失速前瞻提示（默认关闭）。
- 受控的外部自动化来源；每个来源都必须有稳定身份、幂等、撤销和诊断。

### P3：受控智能体工作区

智能体只做读取、解释和草案：选择复盘范围、指出证据、生成项目草案或排期差异。采用前允许编辑，确认后走现有保存/审计路径；没有提供者或模型失败时，手动路径完整可用。

## 9. 功能准入判断

一个新功能只有在同时满足以下问题时才进入产品：

1. 它减少了哪一个具体时刻的负担？
2. 它写入或推导的事实身份是什么？能否回放、去重、撤销和导出？
3. 它与 Today → Review 的核心闭环是什么关系？是否可以从现有入口进入？
4. 它在无数据、来源失效、离线、跨日、跨窗口和移动端如何退回手动路径？
5. 它是否把压力、维护成本或隐私风险转给用户？

答不上来时，功能进入研究或实验区，不进入默认一级 UI。

## 10. 体验指标

指标只用于发现摩擦，不用于给用户打分：

| 指标 | 目标方向 | 解释 |
| --- | --- | --- |
| 首次成功时间 | 下降 | 从空库/模板到第一条确认事实的时间 |
| 记录动作数 | 下降 | 二值、数值、专注结束分别统计；高级字段不计入默认路径 |
| 可回源率 | 100% 的派生主卡可回源 | 点击指标可回到日期、项目或事件 |
| 修正成功率 | 上升 | 误记、撤销、补记、失败重试可以完成且不重复 |
| Review 行动率 | 上升 | 用户从建议进入记录/编辑/忽略的明确动作比例 |
| 压力误报 | 下降 | 普通未记录、跳过、无数据不出现羞辱/惩罚文案 |
| 连接可解释率 | 上升 | 来源卡能说明产生什么、写入哪里、最近结果和恢复动作 |

## 11. 需要真实验证的开放问题

- 一级导航四项在桌面、Dock 和 Android 真机上是否比现有入口更容易发现？
- “同一条事实可同时回到事件、笔记块和日记”是否足够清楚，是否需要更强的来源摘要？
- 项目级 Pause、Exactly 和明确未达成是否真的减少负担，还是增加新状态？
- 事项、习惯、外部自动来源在 Today 合并后，用户是否能快速判断“我要做什么”和“它已经自动发生了什么”？
- 低刺激视觉在长列表、暗色、200% 字体和 TalkBack 下是否仍保留状态差异？

这些问题先通过原型走查、定向浏览器夹具和真实思源/Android 现场验证，再决定是否进入代码路线。

# 三类联动的任务导向梳理（2026-09-28，研究稿，先不开发）

## 目标与现状

新用户应能从一个具体打卡项目出发，回答四个问题：**什么行为会产生记录、记录写给哪个项目、是否还会写入思源文档、怎样确认真的生效**。当前设置把「宿主与插件」「第三方来源联动」「思源文档写入」分为三组，技术边界基本正确，但用户需要先理解 API/来源/文档方向才能找到下一步。三个组里都可能出现“联动”“文档”“写入”字样，且同一打卡目标的设置分散在项目编辑器与多个设置卡片。

证据：`src/render/settings.ts` 的 `host/documents/external` 分组及各来源卡；`src/i18n.ts` 的三个组名和 setupHint；`src/catalog.ts` 的来源模板提示用户另赴设置绑定；`docs/external-integrations-map.md` 的五类数据流与四轴状态；`docs/settings-external-linkage-review-2026-09.md` 的既有分组梳理。本文只做产品信息架构与交互研究，不改变现有事件、来源身份或公开 API 契约。

## 一张面向用户的关系图

```text
用户的打卡项目（目标、单位、排期）
  ├─ 手动点按 / 内置计时 / 问卷 → 打卡事件 → 今日、回顾、统计
  ├─ 第三方行为或指定文档 → 读取/监听/拉取 → 规则校验 → 打卡事件
  ├─ Dock Tomato 专注完成 / 外部插件调用公开 API → 打卡事件
  └─ 已有打卡事实或报告 → 可选写入思源文档（报告、摘要、问卷、锚点）

外部消费方（Task Horizon、Agent 等）可读取小驴公开能力；其“可读取”不等于对方已接入。
```

**打卡事件是事实层**。自动来源最终仍要指向一个有效项目，符合项目的单位与日期/修订规则；写文档是另一条输出链。一个事件可能来自外部来源，也可能触发摘要输出，但两者不互相证明成功。文档写入失败不撤销已经保存的打卡；来源停用或换绑不删除、迁移历史。历史重复的风险在换绑时需要事前说明，不能用“同步成功”一词掩盖。

## 三组各自的用户承诺

| 当前组 | 用户想完成的事 | 数据方向和实际对象 | 首屏应说清 | 不应让用户误会 |
| --- | --- | --- | --- | --- |
| 宿主与插件 | 选择专注工具，查看小驴能否被别的插件/Agent 调用 | Dock Tomato 双向专注会话；API/Task Horizon/Agent 的提供或消费契约 | “选择专注提供方；其余是供其他工具使用的能力状态” | API 已提供、能力已注册不代表第三方已连接，更不代表已有打卡记录 |
| 第三方来源联动 | 用阅读、观看、健康、笔记或外部任务行为自动记到某个项目 | 思阅/思播监听，微信读书拉取，健康/叶归/笔记推导读取指定文档，外部 API 写事件 | “来源行为 → 匹配规则 → 目标项目 → 记录”；列出需要的插件/Key/文档、指标和单位 | 开关已开不代表宿主有事件、轮询读到内容或真的落账；同一行为跨来源可能双计 |
| 思源文档写入 | 把打卡结果或填写的内容放进自己的笔记 | 小驴 → 指定思源文档、日记或插件拥有的块；日记报告、摘要、问卷和锚点各有不同触发 | “输出什么、写到哪里、何时写、失败怎样重试”；明确它是否需要绑定项目 | 文档输出不是“自动记录来源”；问卷写入与打卡关联，但答案正文不应被误以为存进事件备注 |

需要保留五类技术数据流作为卡片的次级说明与诊断依据；一级路径按用户目标组织。建议一级入口文案先做原型测试，例如「自动记录」「写入笔记」「插件能力」，而不是立即全仓替换旧组名。现有书签、设置搜索和旧文档链接需可达。

## 三组内部设置的具体混乱

### 宿主与插件

当前卡片把四种职责并排放在一起：选择默认计时器、显示 Dock Tomato 运行诊断、显示 Agent 能力注册、显示 Task Horizon/API 契约。只有 Dock Tomato 是用户可操作的提供方选择；后三者主要是能力状态或等待对方接入，不能共享同一种“启用”语义。建议拆成「我的专注工具」（选择内置或 Dock Tomato、当前运行状态、失败回退）和「给其他工具使用」（API/Agent/Task Horizon 的提供状态、能力版本、诊断入口）两块；待处理箱属于“运行问题”，应从能力说明中单独呈现。

### 思源文档写入

日记报告、摘要驻留、问卷/锚点虽然都写文档，但触发方式不同：报告是用户手动按当前回顾范围写入，摘要是按日汇总旁路，问卷是一次打卡动作后的答案写入，锚点是特定项目/块的插件拥有内容更新。现在每张卡都重复“目标 → 启用 → 立即写入”，容易让用户误以为所有输出都会自动运行。建议每张卡固定为「写入内容」「触发方式」「目标与所有权」「预览/立即执行」「最近结果」五段；只有有常驻触发的输出显示启用开关，纯手动报告使用“写入本期报告”作为动作，不显示假开关。

### 第三方来源联动

来源卡同时放了格式/凭据、目标项目、启用开关、预览、轮询/拉取、报告和边界长文。不同来源的操作也不一致：监听型应先宿主探测并等待片段，官方拉取型应管理 Key 和立即拉取，文档摄取型应先目标体检/匹配预览，LifeLog 还需要笔记本和映射。建议统一卡片骨架为「来源能产生什么」「输入或宿主前置」「映射到哪些项目」「启用/触发」「验证与最近结果」「限制与隐私」，将高级格式和窗口限制折叠；把“立即刷新”改为来源语义明确的“立即拉取 / 立即读取 / 预览匹配 / 宿主探测”。

三组都应把**目标、动作、状态、问题**分开，避免一个徽标同时表示“配置完成”和“数据已到达”。

## 思源文档与笔记本绑定的专项问题

现有绑定能力已经有一些基础：日记报告/摘要/健康使用文档搜索或 ID 输入，日记和叶归可以加载笔记本列表，`validateBindingTarget` 会在保存时检查目标，设置页还有全部绑定体检。但用户操作仍然粗糙，主要问题是：

- **入口不统一**：有的字段是原始文档/块 ID 文本框，有的提供搜索结果，有的只能点“加载笔记本”后从下拉选择；同一笔记本在日记、健康、叶归、笔记推导卡片中重复选择。
- **目标信息不足**：搜索结果主要显示路径/标题和 ID，已选目标没有稳定的“笔记本 / 文档路径 / 文档名”摘要；块 ID、文档根 ID、笔记本 ID 的差异由用户自己理解。
- **保存反馈弱**：多数操作以单字段保存为边界，保存前缺少目标类型、所在笔记本、权限/可读性和实际用途的确认；启用失败往往在开关动作后才出现。
- **失效修复割裂**：关闭笔记本、删除/移动文档、目标块变成非文档时，各卡片各自报错；集中绑定体检只能查看和打开，不能直接重新选择、比较旧目标与新目标或确认换绑影响。
- **范围语义不直观**：日记模式代表“按笔记本解析当日日记路径”，健康代表“只读指定文档中的收件箱行”，叶归代表“只读笔记本内当日新建段落”，笔记推导还可选择文档或笔记本。当前控件没有把读取范围和是否写入原文放在选择动作旁边。

建议建设一个共享的“思源目标选择器”而不是继续增加 ID 输入框：先选目标类型（文档/笔记本/当日日记），再按笔记本过滤和搜索文档，结果显示名称、层级路径、目标类型和可读状态；保存时保留 ID 作为机器身份，同时保存可展示的快照用于失效提示。选择器要支持“当前目标 / 更换 / 清除 / 打开目标 / 重新检查”，并在换绑前显示旧目标、后续读取或写入范围、历史保留和可能重摄取风险。

统一选择器不应掩盖来源差异。每个使用点仍需在选择器下方明确：写入还是读取、读取哪些块、是否创建文档、触发频率、失败后是否暂停。笔记本列表加载失败、没有打开笔记本、关闭/归档目标、权限或查询失败，都应有具体修复动作；不能把“列表为空”当成“没有笔记本”。

## 以项目为中心的配置闭环

1. **从项目进入**：新建项目或编辑现有项目时提供“记录方式”说明：手动、内置专注、外部来源、问卷；不把来源配置混作项目规则。选外部来源后列出该来源需要的目标单位/类型，并带项目 ID 跳转到对应配置卡。
2. **从来源反查**：每张来源卡首屏显示「产生什么记录」「当前写入哪些项目」「还缺什么」「最近一次有效记录」。未绑定时提供“选择已有项目/创建合适项目”，返回后继续当前配置。多指标来源（微信读书、健康、叶归）按“指标/Marker 项目 → 目标项目”逐项显示，不用单个“已绑定”徽标概括。
3. **保存与验证分开**：统一步骤为选择目标 → 检查单位/范围 → 保存 → 启用 → 预览或探测 → 实际记录核对。只读预览、宿主探测和真实写入分别标记；监听型没有“立即同步”，只能等待一个可观察片段。验证后提供到「回顾记录」的带来源/项目筛选入口，能看到事实详情。
4. **输出另选目的地**：用户从项目、回顾报告或问卷入口选择“写入思源文档”时先展示输出样例和目标；摘要是项目/日期统计的输出，周期报告由用户手动触发，问卷答案随绑定项目的打卡流程写入，笔记锚点回写属于项目旁路。每条输出独立展示最近写入与失败审计。
5. **断开与换绑**：卡片在操作前预告“以后写入停止/新目标生效，旧记录与文档保留”；对有限窗口内可能重摄取的来源提示具体风险。项目被归档、删除、单位变化时显示哪个绑定失效及修复入口，不悄悄改投另一项目。

## 建议的页面形态

- **连接总览**只放三张任务卡：“让行为自动打卡”“把结果写进笔记”“给其他插件使用小驴能力”。每张卡用一句话、一个具体例子和当前进度（如 2/5 来源已配置、1 个目标待修复），进入后再呈现细节。全局数量只是导航，不用总“已连接”徽标。
- **项目侧记录方式区**展示“当前可用的记录方式”，将来源与该项目的映射状态列成清单，提供到设置卡的定向链接。一个项目可有多种方式；同时绑定语义相同的自动时长来源时沿用现有非阻断冲突提示。
- **来源卡首屏**固定五行：用途/记录口径、目标项目、先决条件、触发与验证、最近结果/问题。深层折叠区再放 Key、SQL 模板、Marker 格式、窗口限制和隐私细节。四轴状态继续独立：配置、运行、活动、问题；未知必须写“未探测”。
- **新用户示例**至少覆盖：思阅 20 分钟阅读→分钟项目的一条记录；微信读书每日汇总→阅读项目（与思阅可能重复）；健康文档步数→步数项目；感恩问卷打卡→事件+日记正文；Dock Tomato 一次专注→绑定项目；Task Horizon 只看到小驴契约可用但对方未接入。示例要同时展示失败/空结果，不只展示成功态。

## 设计验收与顺序

先做现状盘点与点击路径原型，再统一状态/文案与项目回链，最后做浏览器交互和真实宿主可观察行为验收。每个来源均以同一检查表核对：前置、触发、目标、单位、事件口径、输出、幂等、停用/换绑、隐私、失败、核验入口。不能仅凭配置已保存或测试宿主假事件宣称第三方已连通。现有 `externalRef`、墓碑、手动优先、写入旁路和失败待处理箱纪律保持有效；实现中若需改这些事实边界，应另行立项评审。

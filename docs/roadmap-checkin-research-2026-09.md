# 小驴打卡后续研究计划（2026-09）

> 登记日期：2026-09-22。状态：**研究排期，暂不开发；已完成现状盘点与初步资料检索，四项充分调研尚未完成**。
>
> 本文把用户提出的四个方向整理为可验证的研究工作。本轮对应任务为 **T-1374（间隔算法）**、**T-1375（项目文档绑定）**、**T-1376（每日日记联动）**、**T-1377（增量竞品复核）**，并以 **T-1378（调研归纳与开发范围决策）** 收口；D-251 记录“先调研、再定范围”。研究完成前不新增数据字段、排期类型、自动写入行为或第三方同步；只有通过本文的决策闸门后，才把明确的结果拆成实现任务。

## 一、为什么先研究

小驴打卡已经有稳定的事件模型、六种排期、跳过/负向习惯、强度分数、项目级笔记锚点和可选的日记报告。四个新想法都可能改变事件含义或产生用户内容，因此不能把“看起来有用”的算法直接接入现有统计：

- 间隔复习会改变“今天是否应该打卡”和提醒时机，容易与现有 `interval`、`quota`、AUTO、SKIP 口径冲突。
- 文档绑定会扩大笔记内容与权限边界；现有锚点已经能回写指定块，继续增加绑定模型前必须证明其必要性。
- 日记联动可能产生自动写入、重复追加和隐私泄露；现有周期报告与每日摘要设计稿已经规定了不同的写入语义。
- 竞品调研必须区分可验证的源码/公开导出格式与营销文案，避免把别人的默认行为当成适合思源的设计。

研究阶段的产出是比较表、最小可行数据模型、隐私/迁移/回滚说明和“立项/不立项”结论；不是功能代码。

## 二、当前基础与已完成能力

### 1. 排期与统计基础

`CheckinSchedule` 当前支持 `daily`、`weekly`、`workdays`、`custom`、`interval`、`quota`。`interval` 已有 `intervalDays + anchorDate`，用于固定日历间隔；它没有“根据表现调整下一次复习日”的语义。事件保存原始记录，完成度、连续、强度和回顾均在计算层推导。

已有相关任务：

- T-1216：复盘呈现与数据入口；
- T-1224/T-1240/T-1241/T-1363：强度、完成质量、成熟度和习惯内核复核；
- T-1226：连续口径重构；
- T-1360：排期字段建议与弹性排期建议；
- T-1276：`maxGap` 断签淡化候选评估，已因现有 quota 的回溯完成语义关闭。

这些任务不等于间隔复习算法。新研究必须先说明它与现有排期、强度分数、跳过日和 at-most 的关系，避免重复创建“再做一个 streak/score”的任务。

### 2. 项目与文档绑定基础

`CheckinItem.noteAnchor` 已支持一个项目绑定一个思源块（文档 ID 也是合法块 ID）：

- 打卡状态可回写 `custom-lv-checkin`；
- 备注/跳过原因可选择追加为子块；
- 失败隔离、有界重试、审计、解绑清理和多窗口语义已在 D-218、T-1231～T-1233 中确定；
- T-1264 已提供已绑定项目的本地选择、清除和经公开 `lsNotebooks + createDocWithMd` 创建文档并自动绑定；
- T-1292/T-1293 已支持渲染块按文档/笔记本作用域读取锚点项目。

因此“每个打卡项绑定指定文档”不是从零开始的能力。待研究的是绑定粒度和用途：复用现有 `noteAnchor`，还是另建“归属文档/日记文档/复习材料”字段。没有明确差异前不新增第二套绑定字段。

### 3. 日记基础

T-1352 已实现 opt-in 的周期报告写入指定日记文档：只追加、失败隔离、手动触发、撤销不删除用户内容。`docs/summary-resident-design.md`（T-1353/T-1166）另有“每日一行摘要驻留文档”设计稿，尚未实现；旧稿将其标为等待隐私决策。本轮把该评估纳入 T-1376，再由 T-1378 根据证据自动采用推荐结论，不再要求用户逐项选方案。旧稿提出单一文档、字段白名单、只追加、默认关闭和零新增公开 API 面，仍须复核这些边界及实现细节。

已有日记/笔记相关任务包括 T-1232、T-1234、T-1292、T-1351、T-1352、T-1353、T-1355，以及 D-218、D-241。新计划只研究它们尚未覆盖的联动触发、用户可见回顾和幂等规则。

### 4. 竞品研究基础

`docs/benchmark-habit-apps-2026-09.md` 已深读 Loop Habit Tracker、Table Habit、Habitica，补充 Habitify、Streaks、Forest、滴答清单、小日常、Atoms、Obsidian Tracker、Habit Tracker 21 和思源第二梯队插件；T-1273、T-1279、T-1356 已把部分结果转为迁入、模板和渲染块任务。

后续研究不重复统计“有多少应用”，而应围绕四个方向补齐算法细节、数据迁移、文档权限和日记闭环证据，并在原文档的“调研续作记录”中追加来源与日期。

## 三、四个研究主题

### 主题 A：间隔复习与记忆曲线（T-1374）

**研究问题**

1. 用户说的“打卡”是一般习惯养成、知识复习，还是两者可选？二者的反馈信号不同，不能共用一个黑箱分数。
2. 先核对遗忘曲线研究的实验对象、测量方式和适用边界，不把固定的“第 1、2、4、7 天”表直接命名为普适科学结论。比较固定间隔、自定义递增间隔、SM-2、FSRS，并评估思源已有复习能力是否更适合承载；半衰期模型与现有弹性 quota 作为补充对照。
3. 最小反馈是什么：完成/未完成、难度、回忆质量、耗时，还是用户主动推迟？缺少反馈时是否应退化为现有排期。
4. 如何处理 SKIP、补记、at-most、跨时区、编辑历史和多窗口并发？算法是否能重放、解释和回滚？
5. 计算成本、隐私和可迁移性如何保证？是否必须保存模型参数，还是由事件确定性重算？

**候选方案（只做比较，不预设选型）**

| 方案 | 适用假设 | 需要验证的代价 |
| --- | --- | --- |
| 现有固定间隔 | 只有完成与否，保持当前日历排期 | 是否已满足需求，是否需要区别“自上次完成起算” |
| 自定义递增间隔 | 用户指定阶段序列，作为可解释基线 | 区分累计日期偏移与相邻间隔；跳过、延期、重启如何推进 |
| SM-2 类 | 有“质量/难度”反馈，强调复习卡片 | 老算法参数和失败重试对习惯项目是否合理 |
| FSRS 类 | 有回忆质量反馈，可比较默认参数冷启动与历史优化 | 调度器与参数优化器分开评估，核对反馈、运行环境、事件迁移和体积 |
| 半衰期成功率 | 只保留少量统计，强调可解释 | 对稀疏数据和不同项目频率是否稳定 |
| 弹性 quota + 建议 | 保留现有数据模型，只建议下一个窗口 | 是否足以覆盖“复习”而不制造自动行为 |

固定间隔、自定义递增间隔、SM-2、FSRS 四类使用同一组样例比较；半衰期模型、quota 和宿主复习能力按适用性增补，不能只拿曲线示意图与一个实现比较。记录各候选的输入、输出、所需反馈和失败边界，并考虑每日负担上限、逾期积压与暂停恢复。

**研究证据**

- 至少两份原始论文/官方算法文档和两个可复现开源实现；
- 用去标识的现有事件样例检验排期兼容性；回忆质量不存在时使用明确标注的合成反馈，不将普通“已打卡”当成“记住了”。回放覆盖冷启动、成功/遗忘、跳过、补记、撤销、乱序、稀疏记录、跨时区和 at-most；模拟只验证机制，不冒充真实记忆效果；
- 输出每个候选的输入字段、输出字段、解释文案、迁移/回滚方案和性能上限；
- 明确“习惯模式”和“复习模式”是否分开。若不能证明分开后的收益，保留现有排期并关闭该方向。

**决策闸门**

只有同时满足“用户能解释下一次安排、旧事件可重算、SKIP/at-most 口径不被改写、无数据时安全退化、能离线测试”才允许形成实现任务。任何需要上传事件、隐式采集内容或修改历史事件的方案直接不立项。

### 主题 B：每个打卡项绑定指定文档（T-1375，绑定与回写分开）

**研究问题**

1. 绑定的目标到底是状态回写块、备注日记、复习材料，还是项目的归属文档？四者应有不同的权限和写入语义。
2. 一个项目是否只能有一个文档？文档被移动、删除、发布或只读时，如何显示挂起并恢复？
3. “打开文档”是否需要块内定位；思源公开 API 是否稳定提供所需字段？内部 DOM 和未验证 SQL 不得成为前置条件。
4. 绑定是否参与渲染块筛选、日记报告来源、导出和导入？若会改变查询口径，如何避免同一项目被重复计入？
5. 绑定信息是否应留在项目 JSON；迁移/导出时是否只导出 ID、还是提供用户确认的脱敏映射？
6. 多个项目绑定同一文档时，现有单个 `custom-lv-checkin` 属性能否正确表达各项目状态，是否存在覆盖？绑定关系可以共享，状态投影却需要明确归属，两者必须分别评估。

**候选方案**

- **复用现有 `noteAnchor`**：把“指定文档”限定为已存在的锚点用途，改进选择器、打开和挂起恢复；改动小，隐私边界清楚。
- **增加明确的 `linkedDocument`**：只有研究证明“状态回写”和“材料归属”需要不同目标时才考虑；必须说明字段关系、优先级和迁移。
- **仅提供文档作用域视图**：不保存新绑定，使用 T-1292 的 doc/notebook 查询；适合报表筛选，不满足项目级快捷打开。

“绑定”只表示项目与目标文档的稳定关系、选择器、打开入口和挂起状态；“回写”表示向目标块写属性或追加内容，必须继续沿用 T-1231～T-1233 的 opt-in、失败隔离和清理纪律。研究中分别评估两者，不能因为已有回写通道就默认需要新增绑定字段，也不能因为有绑定入口就默认允许自动写入。

**决策闸门**

先明确一项可验证、现有 `noteAnchor` 无法表达的必要差异，再判断是否需要新增字段。任何新方案必须核对宿主接口、默认关闭写入、只触碰用户明确选择的文档，并给出解绑清理和只读/发布降级证据；接口仅见源码时记录其兼容等级，不冒充稳定公开契约。

### 主题 C：打卡与每日日记联动（T-1376）

**研究问题**

1. 联动触发是打卡后追加、打开日记时显示待办、日记中点击打卡，还是三者的组合？自动追加是否真的提升复盘完成率。
2. 日记内容是只写汇总数字，还是写项目名、备注、状态和链接？哪些属于敏感内容，哪些必须由用户主动确认。
3. 如何做到多窗口幂等、撤销不误删、失败可重试、重复日期可合并，以及文档被用户手工编辑后的可读性。
4. 如何区分 T-1352 周期报告、T-1353 每日摘要驻留、T-1232 锚点备注，避免同一事件生成三份重复文字。
5. 点击日记中的条目能否回到项目/当天视图；该跳转是否依赖真实宿主能力而非浏览器模拟。

**候选方案**

| 方案 | 说明 | 研究重点 |
| --- | --- | --- |
| 只读联动 | 日记/渲染块读取打卡摘要，用户手动打卡 | 零自动写入，验证是否已满足主要需求 |
| 事件后摘要 | 每日首次事件后追加白名单摘要 | 幂等标记、隐私、文档膨胀、撤销语义 |
| 日记交互块 | 日记中显示项目状态并提供回到插件的入口 | 宿主渲染/点击 API、只读降级 |
| 用户确认写入 | 生成预览，用户确认后追加 | 交互成本与内容控制，复用 T-1352 通道 |

日记路由研究必须固定四个口径：

1. **归属日**：按事件 `localDate` 归档，不能按写入时间或打开页面的时间；补记事件必须说明写入历史日期的位置；
2. **模板**：核对思源原生日记的笔记本、路径、模板和日期定位方式；比较用户指定模板/位置与宿主原生日记，不能只按标题猜测。同日多个笔记本、未建日记及历史补记要有明确规则；
3. **幂等**：比较事件 ID、项目 ID + 归属日、报告范围 + 内容版本等标记；明确逐事件追加与每日汇总的不同粒度，既防多窗口重复，也不吞掉同日多次真实记录；
4. **撤销**：撤销打卡不删除用户文档内容，按 D-218/D-241 评估保留、标记或不再写入三种策略，并说明用户如何发现和清理。

**决策闸门**

先完成 T-1353 的隐私复核，再决定是否自动写入，并将推荐结论记录到 T-1378。旧设计中的 API 与去重规则也须重新取证，不能直接当作已验证实现。研究阶段只比较只读展示、手动预览和自动联动的方案；不实施任何一类功能，不新增定时器、不扫描全库、不把项目备注自动复制进日记。

### 主题 D：同类插件与软件持续调研（T-1377）

**研究问题**

1. 哪些能力有公开源码、公开导出或可复现数据，哪些只是商业应用的不可验证卖点？
2. 同类软件在间隔算法、文档/日记联动、跳过与反内疚设计、提醒和迁移方面的失败案例是什么？
3. 思源集市插件的公开 API、权限、性能和数据模型是否与本插件兼容？是否已有重复实现可直接协作？
4. 哪些借鉴会引入账户、云同步、社交、传感器或后台常驻，超出本插件的本地优先边界？

**研究范围与来源等级**

1. 一级：官方源码、论文、官方导出格式、思源公开 API 与真实宿主验证；
2. 二级：项目 issue、变更记录、公开测试与维护者文档；
3. 三级：应用商店说明、评测和用户讨论，只作线索，不作为行为契约。

每条结论记录来源 URL、版本/提交、访问日期、可复现步骤和适用边界，追加到 `docs/benchmark-habit-apps-2026-09.md`，不另起重复竞品清单。

竞品证据准入规则：源码/论文/官方导出格式可作为行为或数据模型证据；官方文档可作为公开接口证据；issue/变更记录只能证明曾经存在的问题或设计意图；商店文案、评测和用户讨论只能作为待核查线索。没有版本、提交或可复现样例的结论不得进入“吸收清单”。

**决策闸门**

只有当借鉴点能映射到现有事件模型、隐私边界和测试能力，并且没有更简单的本地方案时，才进入候选实现；仅凭“竞品有此功能”不得立项。

## 四、统一研究产出格式（T-1378）

每个主题完成一份结论卡，至少包含：

1. 用户问题与不做的相邻问题；
2. 现有能力、重复任务和数据缺口；
3. 2～5 个候选方案及反例；
4. 数据结构、迁移、隐私、性能、宿主兼容和回滚影响；
5. 可复现样例与失败场景；
6. “采用 / 延后 / 不做”推荐结论、理由和下一步任务边界。

研究完成前的验收只检查文档、来源和离线分析，不运行新功能、不修改生产数据、不生成迁移脚本。T-1378 汇总四张结论卡并记录每个方向的“采用 / 延后 / 不做”推荐及理由；按用户约定自动采用推荐的后续实现范围，不增加逐项等待确认的门槛，但任何实现仍须在研究证据落盘后另拆任务。

## 五、明确不开发边界

- 暂不把 `intervalDays` 改成自适应算法；
- 暂不新增第二套文档绑定字段或全库扫描；
- 暂不自动创建/修改每日笔记，不新增常驻定时器；
- 暂不上传用户事件、笔记正文或训练数据，不引入云端同步；
- 暂不复制商业应用的社交、游戏化惩罚、传感器和后台服务；
- 暂不修改既有 SKIP、at-most、强度分数、日记报告和锚点撤销口径；
- 研究任务完成时可以关闭对应研究项，但不得借此关闭尚未实施的功能。实现任务必须在研究结论和 T-1378 范围决策后另行拆分。

## 六、排期建议

1. **资料批次（T-1377）：** 建立来源矩阵、刷新旧 benchmark，将候选和已吸收能力分开；整个研究期间持续补充；
2. **专题批次（T-1374/T-1375）：** 完成算法样例回放和字段/绑定语义审计，能独立推进的部分并行；
3. **联动批次（T-1376）：** 结合绑定结论完成隐私、日记路由、幂等和撤销方案，复核 T-1353；

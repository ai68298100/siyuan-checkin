## 一、为什么先研究

小驴打卡已经有稳定的事件模型、六种排期、跳过/负向习惯、强度分数、项目级笔记锚点和可选的日记报告。五个新想法都可能改变事件含义或产生用户内容，因此不能把“看起来有用”的算法直接接入现有统计：

- 间隔复习会改变“今天是否应该打卡”和提醒时机，容易与现有 `interval`、`quota`、AUTO、SKIP 口径冲突。
- 文档绑定会扩大笔记内容与权限边界；现有锚点已经能回写指定块，继续增加绑定模型前必须证明其必要性。
- 日记联动可能产生自动写入、重复追加和隐私泄露；现有周期报告与每日摘要设计稿已经规定了不同的写入语义。
- 竞品调研必须区分可验证的源码/公开导出格式与营销文案，避免把别人的默认行为当成适合思源的设计。
- 闪卡联动涉及源块、卡片、复习反馈与打卡事件的不同身份；需先明确宿主调度所有权，防止重复排期、重复记账及查询干扰原生复习。

研究阶段的产出是比较表、最小可行数据模型、隐私/迁移/回滚说明和“立项/不立项”结论；不是功能代码。

## 二、当前基础与已完成能力

### 1. 排期与统计基础

`CheckinSchedule` 当前支持 `daily`、`weekly`、`workdays`、`custom`、`interval`、`quota`。`interval` 已有 `intervalDays + anchorDate`，用于固定日历间隔；它没有“根据表现调整下一次复习日”的语义。事件保存原始记录，完成度、连续、强度和回顾均在计算层推导。

已有相关任务：

- T-1216：复盘呈现与数据入口；
- T-1224/T-1240/T-1241/T-1363：强度、完成质量、成熟度和习惯内核复核；
- T-1226：连续口径重构；
- T-1360：排期字段建议与弹性排期建议；
- T-1276：`maxGap` 断签淡化候选评估，已因现有 quota 的回溯完成语义关闭。

这些任务不等于间隔复习算法。新研究必须先说明它与现有排期、强度分数、跳过日和 at-most 的关系，避免重复创建“再做一个 streak/score”的任务。

### 2. 项目与文档绑定基础

`CheckinItem.noteAnchor` 已支持一个项目绑定一个思源块（文档 ID 也是合法块 ID）：

- 打卡状态可回写 `custom-lv-checkin`；
- 备注/跳过原因可选择追加为子块；
- 失败隔离、有界重试、审计、解绑清理和多窗口语义已在 D-218、T-1231～T-1233 中确定；
- T-1264 已提供已绑定项目的本地选择、清除和经公开 `lsNotebooks + createDocWithMd` 创建文档并自动绑定；
- T-1292/T-1293 已支持渲染块按文档/笔记本作用域读取锚点项目。

因此“每个打卡项绑定指定文档”不是从零开始的能力。待研究的是绑定粒度和用途：复用现有 `noteAnchor`，还是另建“归属文档/日记文档/复习材料”字段。没有明确差异前不新增第二套绑定字段。

### 3. 日记基础

T-1352 已实现 opt-in 的周期报告写入指定日记文档：只追加、失败隔离、手动触发、撤销不删除用户内容。`docs/summary-resident-design.md`（T-1353/T-1166）另有“每日一行摘要驻留文档”设计稿，尚未实现；旧稿将其标为等待隐私决策。本轮把该评估纳入 T-1376，再由 T-1378 根据证据自动采用推荐结论，不再要求用户逐项选方案。旧稿提出单一文档、字段白名单、只追加、默认关闭和零新增公开 API 面，仍须复核这些边界及实现细节。

已有日记/笔记相关任务包括 T-1232、T-1234、T-1292、T-1351、T-1352、T-1353、T-1355，以及 D-218、D-241。新计划只研究它们尚未覆盖的联动触发、用户可见回顾和幂等规则。

### 4. 竞品研究基础

`docs/benchmark-habit-apps-2026-09.md` 已深读 Loop Habit Tracker、Table Habit、Habitica，补充 Habitify、Streaks、Forest、滴答清单、小日常、Atoms、Obsidian Tracker、Habit Tracker 21 和思源第二梯队插件；T-1273、T-1279、T-1356 已把部分结果转为迁入、模板和渲染块任务。

后续研究不重复统计“有多少应用”，而应围绕五个方向补齐算法细节、数据迁移、文档权限、日记闭环和闪卡联动证据，并在原文档的“调研续作记录”中追加来源与日期。

## 三、五个研究主题

### 主题 A：间隔复习与记忆曲线（T-1374）

**研究问题**

1. 用户说的“打卡”是一般习惯养成、知识复习，还是两者可选？二者的反馈信号不同，不能共用一个黑箱分数。
2. 先核对遗忘曲线研究的实验对象、测量方式和适用边界，不把固定的“第 1、2、4、7 天”表直接命名为普适科学结论。比较固定间隔、自定义递增间隔、SM-2、FSRS，并评估思源已有复习能力是否更适合承载；半衰期模型与现有弹性 quota 作为补充对照。
3. 最小反馈是什么：完成/未完成、难度、回忆质量、耗时，还是用户主动推迟？缺少反馈时是否应退化为现有排期。
4. 如何处理 SKIP、补记、at-most、跨时区、编辑历史和多窗口并发？算法是否能重放、解释和回滚？
5. 计算成本、隐私和可迁移性如何保证？是否必须保存模型参数，还是由事件确定性重算？

**候选方案（只做比较，不预设选型）**

| 方案 | 适用假设 | 需要验证的代价 |
| --- | --- | --- |
| 现有固定间隔 | 只有完成与否，保持当前日历排期 | 是否已满足需求，是否需要区别“自上次完成起算” |
| 自定义递增间隔 | 用户指定阶段序列，作为可解释基线 | 区分累计日期偏移与相邻间隔；跳过、延期、重启如何推进 |
| SM-2 类 | 有“质量/难度”反馈，强调复习卡片 | 老算法参数和失败重试对习惯项目是否合理 |
| FSRS 类 | 有回忆质量反馈，可比较默认参数冷启动与历史优化 | 调度器与参数优化器分开评估，核对反馈、运行环境、事件迁移和体积 |
| 半衰期成功率 | 只保留少量统计，强调可解释 | 对稀疏数据和不同项目频率是否稳定 |
| 弹性 quota + 建议 | 保留现有数据模型，只建议下一个窗口 | 是否足以覆盖“复习”而不制造自动行为 |

固定间隔、自定义递增间隔、SM-2、FSRS 四类使用同一组样例比较；半衰期模型、quota 和宿主复习能力按适用性增补，不能只拿曲线示意图与一个实现比较。记录各候选的输入、输出、所需反馈和失败边界，并考虑每日负担上限、逾期积压与暂停恢复。

**研究证据**

- 至少两份原始论文/官方算法文档和两个可复现开源实现；
- 用去标识的现有事件样例检验排期兼容性；回忆质量不存在时使用明确标注的合成反馈，不将普通“已打卡”当成“记住了”。回放覆盖冷启动、成功/遗忘、跳过、补记、撤销、乱序、稀疏记录、跨时区和 at-most；模拟只验证机制，不冒充真实记忆效果；
- 输出每个候选的输入字段、输出字段、解释文案、迁移/回滚方案和性能上限；
- 明确“习惯模式”和“复习模式”是否分开。若不能证明分开后的收益，保留现有排期并关闭该方向。

**决策闸门**

只有同时满足“用户能解释下一次安排、旧事件可重算、SKIP/at-most 口径不被改写、无数据时安全退化、能离线测试”才允许形成实现任务。任何需要上传事件、隐式采集内容或修改历史事件的方案直接不立项。

**最小数据与迁移边界**

1. 现有 `CheckinItem`、历史 `CheckinEvent`、SKIP 事件和 tombstone 保持原样；研究阶段不得给旧事件补写 recall quality，也不得把完成事件批量转换为 review log。
2. 如果未来立项，推荐把“习惯项目”和“复习卡片/复习项目”分开建模：卡片内容、调度状态、不可变 review log 分离保存；习惯项目最多保存一个用户明确确认的关联入口。这样删除/撤销卡片不会删除历史打卡，调度重算也不会改变习惯统计。
3. 任何新增状态必须携带算法标识、算法版本、目标保持率（若有）、上次实际复习时间、下一次 due 和来源时区/日期规则；只保存一个 `interval` 无法可靠迁移到 FSRS。
4. SM-2→FSRS 只有在存在足够的逐次评分日志时才可重算。只有旧 EF/当前 due 而没有 review log 时，必须按冷启动处理并保留原始元数据，不能伪造历史评分。迁移失败应保留原数据并回退到固定排期/只读展示。
5. 复习日期目前以本地日历日为主；如果以后支持小时级 due，必须先确定时区存储与设备时区变化规则。跨时区/DST 不能依赖 `new Date()` 的隐式本地转换。

**验证矩阵（实现立项前的硬门槛）**

| 场景 | 必须断言 | 失败时的安全退化 |
| --- | --- | --- |
| 冷启动/无反馈 | 旧习惯仍按原 schedule；复习项目显示“无调度状态”而非猜测 | 固定 interval 或手动待复习列表 |
| Good/Again 等反馈 | 每个评分的状态、due、解释文案与锁定实现一致；Again 不得等同 Hard | 保留 review log，暂停自动重排 |
| SKIP、at-most、非计划日 | 不进入 recall quality；不改既有强度、quota、负向习惯口径 | 只记录原有事件 |
| 延期、补记、撤销 | 计划日与实际 review 日可区分；删除用 tombstone，回放不重复计数 | 回到上一个可验证状态 |
| 乱序、多窗口、重复导入 | 同一事件/日志幂等，确定性重放收敛到同一 due | 只读冲突诊断，不覆盖较新状态 |
| 跨时区/DST | 同一明确时区规则下日期稳定，不因设备时区隐式漂移 | 日期级调度，禁用小时级自动安排 |
| 迁移/导出 | 无日志冷启动；有日志可重算；算法版本和原始元数据可导出 | 原格式保留、迁移任务可重试 |
| 离线/性能/隐私 | 无网络也可回放；数据量上限有基准；不上传事件、正文或训练数据 | 关闭自动调度，仅提供手动查看 |

**推荐结论（供 T-1378 收口，不立即开发）**

- 普通习惯：保留现有 `interval`、`quota` 和 habit-score；不把艾宾浩斯示意表、SM-2 或 FSRS 偷换成习惯完成率。
- 知识复习：只有在用户明确选择“复习模式”、能够提供四档或等价回忆反馈，并通过上述回放/迁移/并发验收后，才进入独立 review 调度候选；首选锁定版本的 FSRS，透明递增序列可作为无算法依赖的 MVP 基线。
- 兼容与联动：SM-2 仅保留为历史导入/对照；与思源闪卡联动优先只读到期概览和原生复习跳转，调度所有权归宿主，避免两套算法同时修改 due。
- 本轮不新增字段、算法依赖、定时器、后台轮询或自动事件转换。T-1378 需要把本节推荐与 T-1379 的宿主证据合并后，再拆具体小版本和回退方案。

### 主题 B：每个打卡项绑定指定文档（T-1375，绑定与回写分开）

**研究问题**

1. 绑定的目标到底是状态回写块、备注日记、复习材料，还是项目的归属文档？四者应有不同的权限和写入语义。
2. 一个项目是否只能有一个文档？文档被移动、删除、发布或只读时，如何显示挂起并恢复？
3. “打开文档”是否需要块内定位；思源公开 API 是否稳定提供所需字段？内部 DOM 和未验证 SQL 不得成为前置条件。
4. 绑定是否参与渲染块筛选、日记报告来源、导出和导入？若会改变查询口径，如何避免同一项目被重复计入？
5. 绑定信息是否应留在项目 JSON；迁移/导出时是否只导出 ID、还是提供用户确认的脱敏映射？
6. 多个项目绑定同一文档时，现有单个 `custom-lv-checkin` 属性能否正确表达各项目状态，是否存在覆盖？绑定关系可以共享，状态投影却需要明确归属，两者必须分别评估。

**候选方案**

- **复用现有 `noteAnchor`**：把“指定文档”限定为已存在的锚点用途，改进选择器、打开和挂起恢复；改动小，隐私边界清楚。
- **增加明确的 `linkedDocument`**：只有研究证明“状态回写”和“材料归属”需要不同目标时才考虑；必须说明字段关系、优先级和迁移。
- **仅提供文档作用域视图**：不保存新绑定，使用 T-1292 的 doc/notebook 查询；适合报表筛选，不满足项目级快捷打开。

“绑定”只表示项目与目标文档的稳定关系、选择器、打开入口和挂起状态；“回写”表示向目标块写属性或追加内容，必须继续沿用 T-1231～T-1233 的 opt-in、失败隔离和清理纪律。研究中分别评估两者，不能因为已有回写通道就默认需要新增绑定字段，也不能因为有绑定入口就默认允许自动写入。

**决策闸门**

先明确一项可验证、现有 `noteAnchor` 无法表达的必要差异，再判断是否需要新增字段。任何新方案必须核对宿主接口、默认关闭写入、只触碰用户明确选择的文档，并给出解绑清理和只读/发布降级证据；接口仅见源码时记录其兼容等级，不冒充稳定公开契约。

### 主题 C：打卡与每日日记联动（T-1376）

**研究问题**

1. 联动触发是打卡后追加、打开日记时显示待办、日记中点击打卡，还是三者的组合？自动追加是否真的提升复盘完成率。
2. 日记内容是只写汇总数字，还是写项目名、备注、状态和链接？哪些属于敏感内容，哪些必须由用户主动确认。
3. 如何做到多窗口幂等、撤销不误删、失败可重试、重复日期可合并，以及文档被用户手工编辑后的可读性。
4. 如何区分 T-1352 周期报告、T-1353 每日摘要驻留、T-1232 锚点备注，避免同一事件生成三份重复文字。
5. 点击日记中的条目能否回到项目/当天视图；该跳转是否依赖真实宿主能力而非浏览器模拟。

**候选方案**

| 方案 | 说明 | 研究重点 |
| --- | --- | --- |
| 只读联动 | 日记/渲染块读取打卡摘要，用户手动打卡 | 零自动写入，验证是否已满足主要需求 |
| 事件后摘要 | 每日首次事件后追加白名单摘要 | 幂等标记、隐私、文档膨胀、撤销语义 |
| 日记交互块 | 日记中显示项目状态并提供回到插件的入口 | 宿主渲染/点击 API、只读降级 |
| 用户确认写入 | 生成预览，用户确认后追加 | 交互成本与内容控制，复用 T-1352 通道 |

日记路由研究必须固定四个口径：

1. **归属日**：按事件 `localDate` 归档，不能按写入时间或打开页面的时间；补记事件必须说明写入历史日期的位置；
2. **模板**：核对思源原生日记的笔记本、路径、模板和日期定位方式；比较用户指定模板/位置与宿主原生日记，不能只按标题猜测。同日多个笔记本、未建日记及历史补记要有明确规则；
3. **幂等**：比较事件 ID、项目 ID + 归属日、报告范围 + 内容版本等标记；明确逐事件追加与每日汇总的不同粒度，既防多窗口重复，也不吞掉同日多次真实记录；
4. **撤销**：撤销打卡不删除用户文档内容，按 D-218/D-241 评估保留、标记或不再写入三种策略，并说明用户如何发现和清理。

**决策闸门**

先完成 T-1353 的隐私复核，再决定是否自动写入，并将推荐结论记录到 T-1378。旧设计中的 API 与去重规则也须重新取证，不能直接当作已验证实现。研究阶段只比较只读展示、手动预览和自动联动的方案；不实施任何一类功能，不新增定时器、不扫描全库、不把项目备注自动复制进日记。

#### T-1376 补充研究记录（2026-09-22）

**现状证据。** 当前 `src/index.ts` 的 T-1352 是 opt-in 的周期报告：用户指定文档后手动触发，报告通过已有 `appendBlock` 通道追加，失败隔离并保留审计；D-241 明确撤销打卡不删除已经写入的用户内容，也不提供定时自动写入。`docs/summary-resident-design.md`（T-1353/T-1166）是另一份未实现的设计稿，限定单一目标文档、日期与汇总数字白名单、只追加、默认关闭和事件后触发，并明确等待隐私决策。

**宿主接口等级。** 思源 v3.8.4 的 [公开 API 文档](https://github.com/siyuan-note/siyuan/blob/v3.8.4/docs/API.md)可作为 `appendBlock`、`getBlock` 等已文档化能力的依据；v3.8.4 的 [router.go](https://github.com/siyuan-note/siyuan/blob/v3.8.4/kernel/api/router.go)源码还注册了 `createDailyNote`、`appendDailyNoteBlock` 等日记路由，但 API 文档没有对应的公开契约。后两者只能记为固定版本源码证据，不能在插件中假设长期稳定、无副作用或跨桌面/Android/只读模式可用。日记文档的笔记本、路径、模板和同日多笔记本归属也不能按标题猜测。

**方案结论。** 结合现有实现、隐私设计和接口等级，当前推荐如下：

| 方案 | 结论 | 理由与边界 |
| --- | --- | --- |
| 回顾页/渲染块只读摘要 | **采用** | 零自动写入，复用现有事件/报告数据；目标是验证日记联动是否先靠可见性解决需求。只读失败显示“未知/不可用”，不显示为零。 |
| 用户确认预览后写入周期报告 | **采用** | 继续复用 T-1352 的指定文档、`appendBlock`、失败隔离和审计；归属日按事件 `localDate`，撤销不删除用户文字。 |
| 首次打卡后自动追加每日摘要 | **延后** | 必须先完成 T-1353 隐私复核、同日多窗口幂等、用户编辑后的修复路径和真实宿主验收；不新增常驻定时器。 |
| 直接调用 `createDailyNote`/`appendDailyNoteBlock` | **不做（当前阶段）** | 目前只有版本源码证据，缺少稳定插件公开契约；不得把内部路由当成兼容 API。 |

固定语义为：摘要只允许 `localDate`、完成/计划数、记录数、来源计数和可验证的项目/文档链接；使用“日期 + 摘要 schema 版本 + 来源范围”作为每日幂等身份；补记按事件发生日说明，不按写入时间偷换；人工修改不被覆盖，修复通过用户再次确认；不复制备注、照片、题面或正文。日记、项目锚点和未来闪卡汇总必须各自有来源标识，避免同一事件追加三份文字。

**验收结论。** 离线测试可以证明日期归属、幂等键、重复报告与失败恢复；真实思源桌面/Android 仍需验证目标文档解析、日记模板、只读/发布写权限、页签并发和返回项目的触控路径。浏览器或假 DOM 不替代这些现场证据。因此 T-1376 的研究结论已足以限定范围，但自动每日写入不能在没有 T-1353 决策和宿主证据时进入开发。

### 主题 D：同类插件与软件持续调研（T-1377）

**研究问题**

1. 哪些能力有公开源码、公开导出或可复现数据，哪些只是商业应用的不可验证卖点？
2. 同类软件在间隔算法、文档/日记联动、跳过与反内疚设计、提醒和迁移方面的失败案例是什么？
3. 思源集市插件的公开 API、权限、性能和数据模型是否与本插件兼容？是否已有重复实现可直接协作？
4. 哪些借鉴会引入账户、云同步、社交、传感器或后台常驻，超出本插件的本地优先边界？

**研究范围与来源等级**

1. 一级：官方源码、论文、官方导出格式、思源公开 API 与真实宿主验证；
2. 二级：项目 issue、变更记录、公开测试与维护者文档；
3. 三级：应用商店说明、评测和用户讨论，只作线索，不作为行为契约。

每条结论记录来源 URL、版本/提交、访问日期、可复现步骤和适用边界，追加到 `docs/benchmark-habit-apps-2026-09.md`，不另起重复竞品清单。

竞品证据准入规则：源码/论文/官方导出格式可作为行为或数据模型证据；官方文档可作为公开接口证据；issue/变更记录只能证明曾经存在的问题或设计意图；商店文案、评测和用户讨论只能作为待核查线索。没有版本、提交或可复现样例的结论不得进入“吸收清单”。

**决策闸门**

只有当借鉴点能映射到现有事件模型、隐私边界和测试能力，并且没有更简单的本地方案时，才进入候选实现；仅凭“竞品有此功能”不得立项。

### 主题 E：打卡与闪卡是否有联动空间（T-1379）

**研究问题**

1. 先区分三类事实：文档/块是复习材料，卡片/牌组和评分由复习系统管理，打卡事件表示用户完成了某项活动。比较“复习若干卡片”“复习指定文档”“完成一次学习会话”的真实需求，不能把打卡完成直接等同于记忆成功。
2. 映射粒度是项目 → 指定源块、文档范围、牌组，还是具体卡片？核对 `deckID`、`cardID`、`blockID` 的关系、稳定性和移动/删除/重建规则；同一源块的多卡、跨牌组、多个项目共享材料和复习范围重叠要单独建例。已有 `noteAnchor` 不自动授予闪卡写权限，也不能推导为绑定整棵文档树。
3. 哪些接口见于公开 API 文档、哪些只见版本源码，哪些只能由宿主内部 UI 调用？目前没有已验证的插件复习完成事件或会话标识，不预设能可靠自动监听。既要核对路由、请求/响应、权限与版本，也要追到模型层确认调用副作用。
4. 原生闪卡与小驴谁拥有调度？优先研究让宿主维护卡片 due/评分，小驴只呈现学习活动；与 T-1374 一起比较复用原生调度和独立复习模式，不让两套算法同时调整同一学习对象。小驴的 SKIP、at-most 和普通完成质量不直接映射为闪卡评分。
5. 复习次数、独立卡片数、学习时长或会话完成，哪个适合打卡目标？Again 后反复出现的同一卡片、临时预习/强化练习、跳过、未完成会话不能默认等同于多次达标。日记仅考虑汇总与来源链接，默认不复制题面、答案和笔记正文。

**候选联动（均待研究，不代表立项或实施顺序）**

| 方案 | 可能收益 | 待验证条件 |
| --- | --- | --- |
| 只读到期概览 | 查看指定材料待复习情况，减少来回切换 | 必须证明取数不会重置宿主会话/缓存；权限失败显示未知，不能冒充零张到期 |
| 跳转原生复习或源文档 | 保留笔记上下文与原生调度 | 核对公开打开能力、具体范围、桌面/Android 差异；打开文档与打开复习队列分别验证 |
| 复习完成后可选记一次打卡 | 将学习活动汇入现有习惯记录 | 比较手动确认与可验证事件；先取得可靠来源身份，再设计去重，不伪造会话 ID 或自动观察接口 |
| 学习活动汇入每日日记 | 在当天回顾中呈现卡数/时长/材料链接 | 与 T-1376 共用归属日、汇总白名单和写入机制，防止日记与锚点重复追加 |
| 制卡或双向调度同步 | 减少制卡或计划维护步骤 | 与原生能力是否重复、写权限、冲突/回滚和收益均须另证；不预定同步 Anki 或修改原生复习数据库 |

**已核对的一手证据与尚未证实的部分（2026-09-22）**

- SiYuan **v3.8.4** 的 [`router.go`](https://github.com/siyuan-note/siyuan/blob/v3.8.4/kernel/api/router.go)、[`api/riff.go`](https://github.com/siyuan-note/siyuan/blob/v3.8.4/kernel/api/riff.go) 和 [`apicontract/riff.go`](https://github.com/siyuan-note/siyuan/blob/v3.8.4/kernel/apicontract/riff.go) 已初读：存在牌组、按文档树/笔记本获取卡片与到期卡、提交复习/跳过等宿主路由；到期卡投影含 `deckID/cardID/blockID`。该版本 [`docs/API.md`](https://github.com/siyuan-note/siyuan/blob/v3.8.4/docs/API.md) 未检索到 Riff/flashcard 专节，因此当前只登记为固定版本源码可见能力，不能称为稳定的插件公开契约。
- 宿主 [`fetchDueCards.ts`](https://github.com/siyuan-note/siyuan/blob/v3.8.4/app/src/card/fetchDueCards.ts) 有全局/文档/笔记本三种取卡范围；[`model/flashcard.go`](https://github.com/siyuan-note/siyuan/blob/v3.8.4/kernel/model/flashcard.go) 的 `getDeckDueCards` 在已复习卡片参数为空时清空复习/跳过缓存。因此“获取到期卡”目前不能视为无副作用的只读查询，更不能直接用于后台轮询；需复核调用链、会话与多窗口影响后再判断概览能否安全实现。
- [Anki 官方入门](https://docs.ankiweb.net/getting-started.html) 区分 note/card/deck，一份笔记可以生成不同卡片；[官方学习文档](https://docs.ankiweb.net/studying.html) 明确 Again/Hard/Good/Easy 的回忆反馈含义。已初读，尚未运行软件、验证撤销/导出或外部接口；不把 AnkiConnect 当成 Anki 内置官方 API。
- [Obsidian Spaced Repetition 官方仓库](https://github.com/st3v3nmw/obsidian-spaced-repetition) 的 README 已初读：覆盖笔记内卡片、整篇笔记复习、按当前笔记复习与独立的强化练习入口。后续需固定提交、核对调度元数据保存位置、源笔记修改/重命名及移动行为，当前只作为关联方式对照。

**证据与验收矩阵**

输出项目/材料/卡片/牌组/会话映射表、接口等级表、调度所有权表，以及至少一套不产生写入的操作流程。使用临时研究样本核对：同一卡多次评分、同源多卡、重复投递、跨午夜/时区、离线重连、两窗口复习、撤销、源块移动/删除、牌组重建、只读/发布与 Android；按事件发生的 `localDate` 归档。若没有稳定会话或事件身份，明确自动记账不可行，不用抓内部 DOM、轮询私有存储或“卡数下降”推断复习完成。打卡撤销不自动回滚宿主复习，也不删除用户日记文字；两侧撤销及摘要更正需分别解释。

**决策闸门**

必须先证明接口可用且不会干扰原生复习，关联和去重可解释，隐私/只读/离线有明确退路，再由 T-1378 决定采用、延后或不做。研究失败也允许得出只保留手动跳转或完全不联动的结论；本轮不新增闪卡字段、监听器、定时器、制卡、调度改写或第三方同步。

#### T-1397 补充研究记录：思源闪卡重构期的主要方式（2026-09-22）

## 八、T-1375 文档绑定研究增量（2026-09-22）

本节把“每个打卡项绑定指定文档”拆成**关联、打开、回写**三个不同问题。研究结论只覆盖当前已经落地的 `noteAnchor` 语义，不把“能够写入一个块”扩大解释成“已经具备任意文档关联能力”。

### 1. 已实现能力与可验证缺口

| 能力 | 当前证据 | 研究判断 |
| --- | --- | --- |
| 项目保存目标 | `CheckinItem.noteAnchor = {blockId, appendNotes?}`；`validateAnchorBlockId` 只接受 URL 安全块 ID，文档 ID 也落在该格式内 | 可作为一个项目的单一目标块/文档；没有文档类型、路径或权限快照字段 |
| 选择与创建 | 选择器只投影插件已有绑定，按项目名/块 ID 本地搜索；新建走 `POST /api/notebook/lsNotebooks` → `POST /api/filetree/createDocWithMd`，标题斜杠转全角 | 已有低权限、可解释的选择流程；不应改成全库 SQL/全文搜索 |
| 目标存在性 | 回写前调用 `POST /api/block/getBlockInfo`；成功响应在 v3.8.4 源码/真机记录中使用 `rootID`、`box` | 块被移动时应重新解析根文档；删除或不可达进入挂起，不把失败当作“未绑定” |
| 打开 | `openTab({app, doc: {id: rootID}})` 只打开根文档；未验证块内滚动参数，失败回退项目洞察 | “打开指定文档”可交付；“打开并定位块”仍是缺口，不能依赖内部 DOM |
| 状态回写 | `setBlockAttrs` 只写 `custom-lv-checkin`；`appendBlock` 可选追加备注子块；失败隔离、有界重试、审计和解绑清理已实现 | 关联与回写必须分开开关；撤销不删除用户追加内容 |
| 同文档多项目 | 选择器会合并同一 `blockId` 的项目标签，但状态属性是单键 | 绑定关系可以共享；单个状态投影会最后写入覆盖，不能声称能表达每项目并列状态 |

宿主证据等级需分开记录：v3.8.4 `router.go`/`docs/API.md` 是源码或 API 文档证据，`openTab` 的根文档打开来自 SDK 调用；块内定位、只读/发布服务写权限和移动端 WebView 行为仍须真实宿主验收。浏览器或假 DOM 只能证明选择器与降级分支，不替代这些验收。

### 2. 最小数据与迁移语义

推荐继续复用现有字段，不新增第二套“绑定文档”字段：

```ts
noteAnchor?: {
    blockId: string;       // 目标块；文档 ID 也可作为根块 ID
    appendNotes?: boolean; // 独立的用户内容追加开关
}
```

目标文档的标题、路径、笔记本和权限不应复制进打卡 JSON；每次打开或写入前按 `blockId` 重新解析。导出/导入保留 ID 和 `appendNotes`，导入后首次解析失败显示“挂起”并保留原 ID，不能静默改绑同名文档。解绑只清理 `custom-lv-checkin`，不删除文档或用户追加子块；卸载同样不删除用户内容。若未来证明“状态锚点”和“只读材料/归属文档”确实需要两个目标，另立字段并提供显式迁移，不在本任务隐式扩张。

### 3. 用户流程与验收矩阵

1. 编辑项目 → 从已知绑定选择器选块，或选打开笔记本后显式创建文档；保存 ID。
2. 项目洞察/渲染块点击“打开文档” → 解析 `rootID`，打开根文档；块内定位不可用时明确提示并保留项目洞察入口。
3. 打卡回写是独立 opt-in：正常写入属性；备注追加为子块；撤销只改状态投影，不删除已写文字。
4. 移动块/文档后重新解析仍能打开根文档；删除、权限不足、只读或发布模式失败进入挂起/只读降级，恢复访问后再次操作可恢复。
5. Android 真机用触控完成选择、清除、创建、打开和失败提示；窄屏不依赖悬浮 hover。桌面与移动均覆盖两个项目共用文档，确认状态覆盖风险有可见说明。

离线验收应至少覆盖：有效文档 ID、块 ID 与根文档 ID、同文档多项目、块移动、删除/失效、重载恢复、两窗口最后写入、解绑/卸载清理、appendNotes 开关、打开失败回退、只读/发布 403 与 Android 真机。每项都要记录 API 响应、用户提示和是否阻断打卡主路径。

### 4. 一手资料与竞品对照

- [SiYuan v3.8.4 router.go](https://github.com/siyuan-note/siyuan/blob/v3.8.4/kernel/api/router.go) 与 [API.md](https://github.com/siyuan-note/siyuan/blob/v3.8.4/docs/API.md)：用于登记块信息、属性、追加和文档创建路由；Riff/内部路由不能因此当作插件稳定契约。
- [siyuan-plugin-task-note-management README](https://github.com/Achuan-2/siyuan-plugin-task-note-management)：公开说明把任务、笔记/块、日历、习惯和跳转组合在一起，可借鉴“业务对象指向笔记”的入口；仓库公开首页不足以证明其当前每个同步实现的错误/迁移语义，不能直接复制。
- [Obsidian Spaced Repetition README](https://github.com/st3v3nmw/obsidian-spaced-repetition)：同时覆盖卡片和整篇笔记复习，说明“材料入口”和“卡片调度”可分层；它的文件/标签模型不能直接当作思源块 ID 兼容方案。

### 5. 推荐结论（供 T-1378 归纳）

**采用（小范围）：** 复用 `noteAnchor`，补齐“打开根文档、挂起状态、移动/删除降级和移动端触控验收”；保持绑定与回写分离，默认不扩大写入。

**延后：** 新增 `linkedDocument`/多文档列表、块内精确滚动、同文档多项目的并列状态视图；只有出现可复现的独立需求和宿主接口证据后再拆任务。

**不做：** 全库扫描推断绑定、按标题自动重绑、复制文档正文或权限信息、以浏览器 DOM/未公开 SQL 作为打开和迁移前置条件。

因此 T-1375 的最小可开发范围是“已有锚点的关联与打开体验收口”，不是另造绑定体系；具体版本、任务号和是否与日记/闪卡共享入口由 T-1378 在五项研究完成后统一决定。

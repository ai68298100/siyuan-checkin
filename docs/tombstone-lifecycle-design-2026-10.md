# T-1799 墓碑生命周期设计

更新时间：2026-10-16。本文承接 T-1807/D-470 的存储基线，先固定安全语义，不直接改变 Store v3 或删除现有墓碑。

## 当前语义

- 事件墓碑以 `eventId` 为主键，保留 `deletedAt`；如果事件来自 API、思阅、思播、微信读书、叶归或专注来源，还保留 `itemId + source + externalRef`，用于阻止旧窗口或来源重放再次入账。
- 项目墓碑以 `itemId` 为主键，保留 `deletedAt`。`updatedAt > deletedAt` 的真实编辑/导入可以取代墓碑；没有对应项目的悬垂墓碑继续保留，防止旧 Store 把项目和事件并回来。
- `normalizeStore`、`mergeNormalizedStores`、恢复点导入和跨窗口写后校验都会携带墓碑。当前没有时间 TTL、数量上限或自动 GC。
- `appendStoreSnapshotHistory` 最多保留三份完整恢复点，但恢复点导出、旧窗口内存和外部来源重放都可能重新带回历史事实；恢复点数量上限不能直接作为墓碑安全水位。

## 不能直接清理的原因

任何仅按 `deletedAt`、墓碑数量或当前主档是否还存在实体的裁剪，都无法证明以下场景安全：

1. 旧窗口仍持有删除前的完整 Store，在清理后才获得写入机会。
2. 外部来源重复发送同一 `externalRef`，但主档已经没有事件实体可供比对。
3. 用户恢复或导入一个较旧的合法快照，其中包含同 ID 的旧事实；不能把它误判成应被删除的事实。
4. 迁移、JSON/CSV/Loop/Obsidian 导入或第三方来源重放携带旧身份，绕过当前内存窗口。
5. 项目删除后重新创建同名项目；名称不能作为墓碑身份，旧 `itemId` 仍需拒绝复活。

因此，当前安全基线是**保留墓碑身份，先优化读取和表示成本，不做未经证明的删除**。

## 未来可接受的压缩条件

只有引入可持久化、可验证的写入水位后，才考虑墓碑压缩。候选条件需要同时满足：

- 每个写入窗口/来源拥有单调的 generation 或 epoch，并能记录已观察到的墓碑水位。
- 所有仍可能写入的窗口、来源和恢复任务都已确认不持有更旧基线；仅依赖“当前窗口已关闭”不够。
- 恢复点、导入任务和迁移重放有明确的最低允许 generation；低于该水位的输入必须被拒绝或显示冲突，而不是静默合并。
- 外部身份有来源级 checkpoint 或等价的去重账本，能够证明被裁剪的 `externalRef` 不会再次被当作新事实。
- 压缩前后都能重放同一组旧窗口、恢复点、迁移和外部来源夹具，结果保持“删除事实不复活、真实新事实可写入”。

如果不能满足这些条件，方案只能是保留墓碑并采用紧凑表示，例如按身份索引、分桶、压缩序列化或将冷墓碑移入独立归档桶；这些优化不能改变墓碑的逻辑可见性。

## 实施候选

### A. 保留墓碑，优化表示（当前推荐）

不变更数据语义，只测量并优化索引、排序、序列化和恢复点写入。优点是兼容现有窗口、API 和恢复点；缺点是主档长期增长仍需接受或通过分桶缓解。

### B. 引入写入水位后压缩

新增版本化的窗口/来源 generation、确认水位和恢复点最低代际，再按水位压缩墓碑。需要 Store schema、迁移、跨窗口协议和真实宿主联调，不能作为 T-1799 的小修补直接落地。

### C. 用户显式维护操作

提供“生成压缩副本/清理不可恢复历史”的预览和导出，而不是后台自动删除。操作必须列出受影响的来源身份、恢复点和旧窗口风险，并在确认后生成新的基线；这仍需先完成 B 的身份与代际证明。

## 必须通过的守门场景

- 旧窗口在压缩前持有完整 Store，压缩后写入旧项目、旧事件和旧版本。
- 外部来源用相同 `source + externalRef` 重放已删除事件。
- 恢复一个包含旧 ID 事实的合法快照，再写入当前新事件。
- JSON/CSV/Loop/Obsidian 导入和迁移重放旧身份。
- 删除项目及其事件后，重新创建同名但新 ID 的项目。
- 多窗口交错删除、恢复、编辑和卸载收尾。
- 失败写入、读回错配和重载后，主档、墓碑和恢复点的结果一致。

## 当前决定

T-1799 继续保持设计中。现阶段不按时间或数量删除墓碑，不引入 schema v4，不把 T-1807 的内存 host 基准当作真实宿主证明。下一步先把 T-1807 的真实 `saveData`/重载证据和大附件数据补齐，再决定是否进入 A 的表示优化；只有形成可验证 generation/水位协议后，才评估 B。

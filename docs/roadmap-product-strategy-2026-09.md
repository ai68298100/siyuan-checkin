# 小驴打卡产品战略与生态调研路线

更新时间：2026-09-23

本文把当前仓库路线、已完成能力和本轮公开资料调研合并为长期规划参考。它是研究与候选方向，不等于所有条目已经立项。涉及外部插件、真实 Android 行为和用户隐私的条目，仍需经过相应验收或决策门。

## 一、产品定位

小驴打卡适合定位为：**思源笔记里的本地优先行为数据工作台**。

它的核心价值不是再做一个待办清单，也不是把打卡做成游戏，而是把“想养成的行为”变成可记录、可解释、可回看、能和笔记发生关系的长期数据。用户应当可以在思源的今日页、文档块、日记、页签、dock 和移动端快速记录；在回顾页回答“做了什么、哪里断了、为什么断、下一步要怎么调整”；在需要时让其他插件或外部来源提供可验证的事实。

建议长期坚持四个定位边界：

1. **本地优先**：事实数据在思源工作区，外部来源 opt-in，失败可诊断，用户可以导出和恢复。
2. **事件优先**：保存原始事件、来源、时间和外部身份，统计是可重算投影，避免指标写死或多来源重复累计。
3. **笔记原生**：回写只写入用户明确指定的位置，追加优先，保留锚点、审计、撤销和失败隔离。
4. **低压力**：允许 SKIP、容错和补记，重点展示趋势和可行动建议，不用惩罚、掉级、社交排名逼迫用户。

明确不作为主路线的方向：通用任务管理器、账号/社区体系、云同步服务、系统级后台常驻、RPG 惩罚经济、读取第三方私有数据库、万能 AI 写入口。

## 三、未来的大方向

下面的 16 条是产品主方向，第七节另补 7 个横切方向，共 23 项。P0 是可靠性与入口基础，P1 是产品差异主线，P2 是生态和持续维护方向；优先级不改变证据分类，现场项跳过后继续本地队列。

### P0：先把产品变得可靠、好用、易进入

**1. 真实宿主与移动端可靠性工程**

长期目标是关闭 T-1344/T-023/T-033/T-129/T-1256/T-1173/T-1388 等现场验收窗口。本轮只推进可自动复现的夹具和缺陷修复；桌面、页签、dock、Android WebView、键盘、安全区、重载、多窗口和外部插件现场证据保持开放。浏览器响应式模式不能算 Android 验收。

**2. “今日行动台”成为唯一主入口**

今日页应只回答三件事：现在要做什么、完成到哪里、怎样快速记录。把今日打卡、待处理、专注入口、最近漏卡、今日累计和笔记入口组合成一个可收缩的行动台；回顾和高级统计退到第二层。桌面、dock、移动端共享语义，密度和控件按 surface 调整。

**3. 快捷入口与命令系统重做**

完成历史截图 backlog：添加入口对话框/底部 sheet、图标描述符与 fallback、desktop/sidebar/mobile 能力矩阵、未知第三方命令标记、独立的显示/执行/能力元数据，以及首帧和开关几何修复。视觉隐藏只能影响展示，不能删除命令或用户配置。

**4. UI 维护系统化**

把错位、截断、滚动穿透、空态闪烁、浮层残留、主题冲突、焦点丢失和键盘遮挡建立成长期台账。抽出统一的保存中/成功/失败/重试/空态/加载骨架/依赖状态组件，降低页面之间的差异；每个版本固定通过 320px、280px dock、短横屏、长文本、中英文和双主题矩阵。

**5. 新手引导与渐进式复杂度**

新用户先看到 3～5 个精选模板、一个今日记录和一个可解释的回顾；高级排期、配额、at-most、来源映射和渲染块按需展开。把“第一次成功记录”作为首要指标，避免第一次打开就暴露完整数据模型。

### P1：形成与普通打卡软件不同的产品价值

**6. 习惯内核二期：从连击转向节奏与恢复**

在现有 SKIP、容错、弹性周期、quota、at-most 基础上，增加可解释的“应做节奏/逾期率/恢复状态/最近稳定区间”。连续天数只做辅助指标，避免一次漏打让用户失去全部进展。参考 OpenHabitTracker 的逾期率视角和 Loop 的任意频率，但不改变已有事件语义。

**7. 情境化记录与轻量复盘**

允许用户在完成或跳过时可选记录心情、阻力、地点/场景、简短备注和“下次降低难度”的原因。它们先作为可选事件附加字段或独立只读投影，不得让普通打卡变成填问卷。目标是回答“为什么没有做”，而不只是统计“做没做”。

**8. 回顾 2.0：从图表集合变成决策工具**

每个图表都应给出可行动结论：哪几个项目正在失速、在哪些星期或场景容易漏、目标是否过高、最近一次调整是否有效。报告应能展开到原始事件、修订版本、来源和统计截止时间，并明确区分事实、推断和建议。

**9. 笔记原生渲染块二期**

在 today 块基础上做受限数据集、分组/标签聚合、日期跳转、汇总表达式和可组合卡片。借鉴 Obsidian Tracker 的可枚举函数思路与 Easy Tracker 的模块化；小驴自身必须实现显式白名单解析，禁止任意 JS、任意 HTML、无限查询和把正文复制成第二份事实数据。

**10. 日记与周期报告成为可控出口**

继续完善周报/月报、每日摘要、绑定文档选择、预览、追加、重试和撤销说明。参考 Notion 的重复模板与思源 Diary Calendar 的 hpath 定位，但所有写入都必须由用户显式开启，不能用常驻后台任务偷偷改用户文档。

**11. 模板与习惯组合（habit stacks）**

把模板从“单个项目预设”升级为可预览的生活场景组合，例如晨间、学习、运动、睡前、创作；每个组合显示包含哪些项目、排期、默认值和可选项。模板仍是纯内容资产，不改变数据模型，不做云端模板市场。

**12. 外部来源适配器平台化**

继续落实“登记→接入→结算→身份→治理”五段框架。优先完成思阅、思播、健康、微信读书等有明确公开接口或用户主动导入的来源；每个适配器必须有能力发现、来源说明、唯一 `source + externalRef`、失败诊断、撤销/墓碑和离线降级。拒绝读取第三方私有数据库或依赖未版本化 DOM。

**13. 导入、导出与迁移成为一等能力**

提供稳定的 JSON/CSV/TSV/Markdown 导出、范围导出、诊断包和从 Loop/Obsidian/Logseq/其他公开格式导入。导入前显示不可迁移语义，例如排期、SKIP、颜色、备注和 maxGap 的差异；导入必须可预览、可撤销、可重复执行而不重复记账。

### P2：生态、智能和长期可持续性

**14. 公开 API 与思源插件生态网络**

完成 API v5 文档、能力协商、错误码、弃用周期和契约测试包，争取至少两个真实消费方。先提供只读投影和受限写入，再考虑更复杂的双向联动；合作插件不应依赖小驴私有存储。

**15. 受控智能体成为解释器与规划助手**

让智能体解释数据、生成复盘问题、提出模板/排期调整草案；写入继续走“草案→差异预览→用户确认→冲突检查→审计→可撤销”链路。智能体不能直接改事件、批量删除、自动惩罚或在未配置模型时影响基本功能。

**16. 性能、无障碍和恢复能力常态化**

维护 10k/100k 事件、低端设备、跨窗口和多来源组合基线；日历使用真正的键盘网格语义，所有弹层恢复焦点，系统启用 reduced motion 时取消庆祝动效；持续演练升级、降级、损坏数据隔离、导出恢复和冲突合并。

## 四、建议的版本节奏

### 阶段 A：下一批维护版本

- 先完成架构与日期契约、今日投影和本地可复现 UI 检查；真实宿主和 Android 证据留在独立待验队列。
- 快捷入口先做能力/显示/执行分离和图标 fallback；历史截图 backlog 的视觉实现仍等截图齐全和明确开始信号。
- 收口 T-1386 的来源设置、断开、重试、多来源展示。
- 修正路线文档版本滞后问题，确保路线文件与 v18.2.1 一致。

### 阶段 B：产品差异化版本

- 习惯内核二期的逾期率/恢复视图。
- 情境化记录与决策型回顾。
- 渲染块二期、日记报告和模板组合。
- 导入/导出迁移体验升级。

### 阶段 C：生态与智能版本

- 本地推进 Task Horizon、Dock Tomato 等公开契约与 mock consumer；真实消费方联调列为独立外部依赖。
- 来源适配器准入清单与公开契约测试包发布。
- 受控智能体扩展到复盘和结构化草案。
- 性能、无障碍、恢复演练成为发布固定门槛。

### 条件批次

- 微信读书适配器：先完成 Key 申请流程、API 条款/限流核对和用户需求确认。
- 轻量积分/愿望兑换：只有用户明确提出后再评审；即使启动，也只能是默认关闭的单轨积分与愿望清单，不引入掉分、等级和惩罚。
- 自建同步：维持“不立项”决策，除非思源同步被真实证明不足，并先完成隐私、密钥、冲突和迁移评审。

## 五、每个候选方向的准入标准

只有同时满足以下条件，才从“研究参考”变成正式 TODO：

1. 能明确说明用户要解决的场景和收益。
2. 能映射到现有事件、项目修订、`localDate` 和来源模型。
3. 不需要复制第三方私有数据或私有实现。
4. 有公开接口、公开导出格式或可自洽的本地实现。
5. 有失败、撤销、迁移和回退方案。
6. 能在桌面、页签、dock、Android 和双主题中定义验收证据。
7. 不破坏本地优先、低压力和“显示与执行分离”的产品边界。

## 七、补充的长期大方向

原有 16 个方向继续有效，以下七项是本次完整审计后补入的长期方向，总方向数扩展为 23 项。

### 17. 提醒与注意力策略

提醒不应只是今日页里的一个按钮，而应是可解释、可关闭、可恢复的投影层。基于 reminders.ts、priority-reminder.ts 和 reminder-projection.ts，后续可以做：

- 用户控制的安静时段、提醒窗口和每项提醒策略。
- 重复通知防抖、跨窗口去重、来源说明和失败诊断。
- 将提醒原因连接到排期、逾期率、专注状态和今日行动台。
- 宿主能力缺失时降级为页内提示，不自动启动系统后台任务。
- 记录关闭、延后和失败原因，但不把提醒行为当成打卡事实。

### 18. 项目生命周期与数据治理

归档、恢复、墓碑、冲突、备份和撤销要形成一个可解释的数据治理层，而不是分散在各个功能里。基于 model.ts、storage-transaction.ts、diagnostics.ts 和 merge 路径，后续可以做：

- 项目生命周期状态图和事件保留规则。
- 归档/恢复/删除前的影响预览。
- tombstone、冲突修订和外部身份的可读审计。
- 导出快照、损坏条目隔离、恢复点和恢复后校验。
- 清理用户控制面：明确哪些是事实、哪些是投影、哪些可以撤销。

### 19. 本地隐私与控制中心

本地优先需要可见的控制面来建立信任。基于 export、diagnostics、偏好和来源设置，可以逐步提供：

- 数据范围、来源、文档写入和外部联动的总览。
- 一键导出、按范围导出、诊断包预览和敏感字段说明。
- 外部来源逐项断开、已写入事件保留规则和重新接入说明。
- 删除/撤销前的影响清单，不提供不可逆的隐藏操作。
- 不增加遥测；质量指标只来自本地测试、显式导出和用户主动查看。

### 20. 架构边界与扩展准入

插件功能变多后，架构纪律本身成为产品质量的一部分。后续固定维护：

- 代码依赖由 host 编排层指向 render、features 和 model；纯 projection 不反向依赖宿主、渲染或 IO。`features/*` 中的宿主适配模块另列副作用边界。
- recordEvent、recordExternalEvent、appendBlock、偏好保存等副作用入口白名单。
- 新来源必须有 descriptor、唯一身份、settlement、治理、撤销和测试。
- 新 API 必须同步 source、manifest、文档、contract fixture 和兼容/弃用说明。
- 新 UI 必须同步 i18n、ARIA、窄宽度、双主题和 reduced motion 守门。
- 通过静态 import graph、文档同源和能力矩阵检查阻止边界回潮。

### 21. 本地产品质量度量

不引入后台遥测，也可以用本地证据判断路线是否有效：

- 首次成功记录需要的步骤数和失败回退次数。
- 今日主入口到记录完成的纯 UI 时序预算。
- 投影确定性、迁移幂等率、重复外部事件拒绝率。
- 导入/回写/恢复的失败可解释率和成功恢复率。
- 10k/100k 事件的索引、投影、渲染和导出预算。
- CSS 体积、键盘/ARIA 门禁、窄宽度和主题覆盖率。

这些指标只用于本地测试和显式诊断，不上传用户数据，也不改变产品中的惩罚或排名逻辑。

## 八、从 v18.2.1 继续前进的连续路线

1. v18.2.1 发布后，先完成文档真值、状态矩阵、架构边界和自动化证据收口。
2. 自主泳道推进今日行动台、提醒投影、节奏/恢复、回顾证据和导入预览。
3. 继续推进渲染块白名单、报告预览、模板组合、来源契约和 API mock consumer。
4. 将真实宿主、Android、外部插件和 Task Horizon 消费端作为独立 host-pending 队列，不因本地完成而误关闭。
5. v18.3.x 聚焦本地可交付的小步批次；v19 聚焦笔记原生、数据治理和模板组合；v20 聚焦受控智能体与质量控制面；v21 聚焦公开生态消费方；v22 聚焦性能、恢复和隐私/同步决策门。
6. 每一轮生态调研只吸收 1～3 个与现有事件、投影和笔记边界相容的能力，完成后回到同一条自动化—现场验收—复盘循环。



### 22. 时间与日历语义契约

localDate、时区切换、夏令时、跨午夜、周期边界和日期修订是所有功能的横切基础。后续应建立单一日期契约，覆盖 model、calendar projection、API、报告、导入导出和来源结算：

- 所有纯函数显式接收时区和当前日期，不读取系统隐式时钟。
- 跨午夜和跨日来源在接入层切段，在核心层按 localDate 计算。
- 时区切换、夏令时、补记、撤销和历史修订都有可回放样例。
- 今日、回顾、渲染块、报告、API 和导入预览不得各自解释日期。
- 日期边界失败时优先 fail-closed，并显示统计截止时间和来源。

### 23. 可保存视图与筛选工作台

参考 OpenHabitTracker 的相对日期和可配置显示，将 Today/Review 的筛选做成可保存的本地视图：

- 支持相对日期、项目、分组、来源、状态和完成率组合。
- 视图只保存查询偏好和排序，不复制事件，不改变项目模型。
- 导出、报告和渲染块显示当前筛选范围，避免用户误以为是全库统计。
- 视图失效时显示缺失项目/来源并提供恢复默认入口。
- 桌面、dock、移动端共享查询语义，surface 只改变布局。

这两个方向属于横切基础设施，优先级高于新增页面；没有它们，节奏、回顾、导入和生态输出容易产生日期或范围不一致。
